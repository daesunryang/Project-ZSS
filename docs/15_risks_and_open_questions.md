# 15. 위험 요소 및 미결정 사항

## 1. 주요 위험

| 위험 | 영향 | 완화 |
|---|---|---|
| 기능 범위 과대 | 개발 지연/품질 저하 | vertical slice, MVP 제한 |
| NPC 수 증가 | 서버 AI 부하 | 계층형 시뮬레이션, 중앙 스케줄러 |
| 대규모 월드 | 메모리/렌더링/내비게이션 부하 | 구역 스트리밍, 프로파일링 |
| 멀티플레이 동기화 | 상태 불일치/치트 | 서버 권한, RPC 검증 |
| 동적 건축 | navmesh 갱신 비용 | 구역/타일 단위 갱신 실험 |
| 복잡한 관계 AI | 예측 불가/테스트 어려움 | 이벤트 기록, 결정론 seed, 디버그 도구 |
| 저장 데이터 복잡성 | 세이브 손상/마이그레이션 | 스키마 버전, 백업, 원자적 저장 |
| 시뮬레이션 오프라인 진행 | 플레이어 부재 중 과도한 손실 | 서버 옵션 및 계산 상한 |
| 비밀 정보 멀티플레이 | 클라이언트 정보 누출 | 플레이어별 knowledge projection |
| AI 행동의 부적절한 묘사 | 편향/낙인 | 정신적 고통과 폭력 원인을 단순 연결하지 않음 |

## 2. 미결정 질문

아래 항목은 후속 기획에서 결정해야 한다. Claude Code는 개발을 막지 않는 임시 가정을 명시하고, 임의로 제품 정책을 확정하지 않는다.

### 제품/플레이
- 최종 최대 동시 플레이어 수는 몇 명인가?
- 공개 서버와 개인 서버 중 어떤 것을 우선 제공할 것인가?
- 플레이어 사망 후 같은 캐릭터로 복귀 가능한가?
- 캐릭터 사망/좀비화 여부는 서버별로 조절할 것인가?
- PvP 및 플레이어 절도는 허용할 것인가?

### 월드
- 4km × 4km 후보 크기가 적절한가?
- 월드가 절차 생성인가, 수작업 맵인가, 혼합인가?
- 서버가 비어 있어도 작물/부패/감염이 진행되는가?
- 지역별 자원 재생성은 있는가?

### NPC/사회
- 서버당 NPC 최대 수는 얼마인가?
- NPC 수용/영입 제한은 쉘터 크기/식량/침대와 연동하는가?
- 연애는 독점 관계를 기본으로 할 것인가?
- NPC의 성인 관계/가족/출산 콘텐츠는 어디까지 포함할 것인가?
- 배신/살인 같은 중대 행동의 빈도와 금지 조건은 무엇인가?
- NPC 개인 비밀을 다른 플레이어에게 얼마나 공개할 것인가?

### 세계관/동물
- 감염 가능한 동물의 최종 종 목록은 무엇인가?
- 동물 감염은 물림만 가능한가, 혈액/체액도 가능한가?
- 치료제는 감염 후 어느 단계까지 효과가 있는가?

### 운영/배포
- 계정/친구 초대/서버 브라우저가 필요한가?
- 모드와 사용자 제작 콘텐츠를 지원할 것인가?
- 서버 관리 명령/백업/관리자 도구는 어떤 범위인가?

## 3. 미결정 항목 처리 규칙

- 구현이 가능한 경우 설정값/인터페이스만 먼저 만든다.
- 제품 정책과 밸런스를 하드코딩하지 않는다.
- 추후 변경 비용이 큰 항목은 ADR로 결정한다.
- 가정으로 진행한 경우 코드 주석과 문서에 `PROVISIONAL`을 표시한다.

## 4. Phase 0 부트스트랩 임시 가정 (PROVISIONAL)

Phase 0 구현 중 문서에 근거가 없어 개발을 막지 않는 범위에서 임시로 정한 사항이다. 모두 **확정이 아니며**, 변경 비용이 커지기 전에 검토/ADR이 필요하다.

|---|---|---|---|
| P0-1 | 테스트 프레임워크 | 외부 의존성 없는 자체 headless 러너(`tests/run_tests.gd`, `TestCase`). GUT 등은 Godot 4.7.2 호환성을 검증하지 못해 도입하지 않음. | 자체 러너 유지 vs GUT/GdUnit4 도입. 도입 시 4.7.2 호환 버전 고정과 기존 테스트 이전 방법. |
| P0-2 | 서버/클라이언트 역할 선택 | 같은 메인 씬에서 `-- --server`/`-- --client` 인자, 없으면 `dedicated_server` feature tag면 서버, 그 외 클라이언트. `--headless`만으로는 서버로 간주하지 않음. | 역할 선택 방식과 전용 서버 전용 진입 씬 분리 여부. |

| P0-4 | 클라이언트 export 플랫폼 | "Windows Client"(x86_64) 프리셋만 둠(docs/00 "Windows PC 우선" 임시값 반영). | Linux/macOS 클라이언트 지원 여부. |

| P0-7 | 로그 형식/출력 | `<UTC ISO8601>Z [LEVEL] [subsystem] message \| key=value ...` 형식으로 stdout(ERROR/FATAL은 stderr). 키 이름에 password/token/secret/auth/credential이 포함되면 값을 마스킹. 파일 로깅은 Godot 기본 설정을 그대로 사용. | 서버 로그 파일 위치/로테이션/보존 기간, 구조화(JSON) 로그 필요 여부. |

### 4.1 Phase 0에서 검증하지 못한 항목

- 실제 GPU 렌더링 창에서 클라이언트 실행(검증 환경에 디스플레이 없음; 클라이언트는 headless 디스플레이 드라이버로만 실행 확인).
- export template를 사용한 실제 실행 파일 export(템플릿 미설치). `--export-pack`으로 만든 `.pck`를 에디터 바이너리로 실행하는 것까지만 확인.
- dedicated server export 시 `dedicated_server` feature tag에 의한 자동 서버 역할 선택(단위 테스트로 파서 로직만 검증).
- Windows 환경에서의 실행.

## 5. Phase 1 네트워크/플레이어 임시 가정 (PROVISIONAL)

Phase 1 구현에서 문서에 근거가 없어 **조정 가능한 설정값/인터페이스로만** 둔 사항이다. 모두 확정이 아니다.

| # | 항목 | 임시 가정(현재 구현) | 결정 필요 사항 |
|---|---|---|---|
| P1-1 | 플레이어 식별/인증 | 인증·계정 없음. 클라이언트가 `--player-key=<영숫자_- 1~64자>`를 보내고 서버가 `player_key → player_id`로 같은 플레이어를 찾는다. 키를 알면 누구나 그 플레이어로 접속할 수 있다(보안 없음). 키는 저장 데이터(world_state.json, players/*.json)에 평문으로 남는다. | 인증 방식(서버 암호, 토큰, 플랫폼 계정 등)과 신원 저장 방식. docs/00 §8 "서버 목록/초대/암호/관리 도구"와 연동. |
| P1-2 | 엔티티 ID 형식 | `<kind>_<6자리 이상 순번>`(예: `item_000042`), 다음 순번과 삭제 ID tombstone을 world_state에 저장. | UUID 전환 여부(docs/14 §1은 "UUID 또는 안정적인 문자열 ID"). 여러 서버/월드 병합 계획이 있으면 UUID 권장. |
| P1-3 | 프로토콜/게임/저장 버전 관계 | `BuildInfo.PROTOCOL_VERSION`(=1)이 정확히 일치해야 접속 허용. 게임 버전(`0.0.1`)은 로그만 남긴다. 저장 문서는 종류별 `schema_version`(item/player/world=1, manifest=1). | 버전 호환 정책(하위 호환 허용 범위, 업데이트 강제 방식). |
| P1-4 | 포트/인원/바인드 | `data/tuning/network_settings.tres`: port 24680, max_players 4(docs/00 초기 1~4 검증 목표), bind `*`, ENet 연결 여유분 +2(가득 찬 서버가 `server_full`을 응답하기 위함). `--port=`로 덮어쓰기 가능. | 기본 포트, 최대 인원, 서버 권장 사양. |
| P1-5 | 핸드셰이크/거절 | 접속 후 5초 안에 join 요청이 없으면 `handshake_timeout`, 거절 사유 전송 후 0.25초 뒤 연결 종료. 거절 코드: `protocol_mismatch`, `bad_type`, `bad_player_key`, `server_full`, `player_key_in_use`. | 거절 사유 표시(UI)와 재시도 정책. |
| P1-6 | 개발용 월드 내용 | 새 월드에는 `data/tuning/dev_world_seed.tres`의 `dev_test_item` 1개를 (6, 0, 0), 셀 `cell_0_0`에 배치. 셀 스트리밍 전까지 모든 월드 아이템의 location_id는 `cell_0_0`. P2-T3에서 음식·물·파이프가 추가됐다(§11 P2-121). "새 월드의 아이템은 1개"를 전제로 하던 테스트는 자기 seed를 명시한다 | Phase 3 월드/루팅 생성 규칙으로 교체. |
| P1-7 | 월드 아이템 위치 저장 | `schemas/item_instance.schema.json`에 좌표 필드가 없어, 월드에 놓인 아이템의 좌표는 world_state의 `inventory.world_item_positions`(item_id → [x,y,z])에 따로 저장. | 스키마에 위치(transform) 필드를 추가할지, 셀 파일로 옮길지(docs/10 §3 cells/). |

| P1-9 | 메시지 채널/신뢰성 | ch0 reliable ordered: join/거절/입퇴장/줍기/인벤토리. ch1 unreliable ordered: 이동 의도, 위치 스냅샷(20Hz, tick 번호로 오래된 것 폐기). docs/08 §7 "측정 후 선택"에 따라 측정 전 임시값. | 네트워크 프로파일링 후 채널/전송 모드/스냅샷 주기 확정. |
| P1-10 | 요청 빈도 제한 | 토큰 버킷: 이동 60/s(버스트 30), 줍기 4/s(버스트 4). | 측정 후 조정. 반복 위반 peer 처리(경고/추방) 정책. |
| P1-11 | 줍기 규칙 | 서버 위치 기준 거리 ≤ `pickup_range_m`(2.5m), 인벤토리 슬롯 20개(스택 단위), 먼저 승인된 요청만 성공. 무게/부피 없음. | 인벤토리 용량 모델(무게/부피/장비 슬롯), 상호작용 시간. |
| P1-12 | 저장 시점/보존 | 새 월드 생성 시, 줍기 성공 직후, 플레이어 퇴장 시, 서버 종료 시, 60초 주기 autosave에 전체 월드를 저장. 이전 세대 백업 3개 보존. 저장 루트 `user://saves`(`--save-root=user://...`로 변경 가능). | 저장 주기와 데이터 손실 허용 범위(docs/10 §5: 테스트로 결정), 증분 저장 필요 여부. |
| P1-13 | 저장 원자성 범위 | 파일별 임시 파일 → 검증 → 백업 → rename. 여러 파일 rename 도중 프로세스가 죽으면 파일 간 세대가 섞일 수 있고, 이 경우 직전 세대가 backups/에 남는다(자동 세대 일치 복구는 아직 없음). | manifest 기준 세대 일관성 검사/자동 롤백 도입 여부. |
| P1-14 | 플레이어 상태 범위 | PlayerState는 player_id, player_key, position, yaw, inventory_id, last_saved_at_utc만 저장(docs/14의 health/needs/infection 등은 Phase 2). 월드 시간(WorldClock)이 없어 저장 시각은 UTC로 별도 필드. | WorldClock 도입 후 `last_saved_at`(월드 시간) 추가. |
| P1-15 | 동시 접속 시 월드 시간 | 월드 시간 자체가 아직 없음(docs/00 "마지막 플레이어 퇴장 시 일시정지" 제안은 미구현). | WorldClock 티켓에서 결정. |

### 5.1 Phase 1에서 검증하지 못한 항목

- 실제 네트워크(다른 머신, 지연/손실/NAT) 환경. 모든 테스트는 localhost ENet.
- 클라이언트 렌더링 창에서의 이동 표시와 입력(카메라/입력은 P1-4로 별도).
- 장시간(soak) 서버 실행, 메모리/대역폭 측정, 4명 초과 부하.
- 저장 도중 프로세스 강제 종료(kill -9) 시 복구 — 단위 테스트는 손상 파일 복구까지만 검증.

## 6. Phase 2-B(생존) 및 P2-0 임시 가정 (PROVISIONAL)

Phase 2 계획(조정자 승인)의 B묶음과 공통 seam(P2-0)에서 정한 임시값이다. **[사용자 확인 필요]** 표시는 제품/세계관 결정이라 사용자가 확정해야 한다.

### 6.2 Phase 2-A에서 검증하지 못한 항목

- 성능 실측: 틱당 AI 시간, 좀비 수에 따른 서버 부하를 재지 않았다. 상한 64·틱당 8은 측정 없이 둔 값이다(CLAUDE.md §10).
- soak 범위: 좀비 20~24마리, 3시간을 2초 틱으로 돌린 단위 테스트뿐이다(P2-T1부터 배율 가속 대신 긴 틱). 실제 틱 간격으로 여러 시간 서버를 돌려 보지 않았다.
- 네트워크: 좀비는 N1a에서 복제된다(소음은 서버 내부 전용이라 복제하지 않는다). 두 클라이언트가 같은 좀비를 보는지는 `zombie_net_test`와 P2-Z에서 검증한다.
- 실제 서버 프로세스에서 좀비가 플레이어를 공격하는 흐름: 스모크 테스트는 12마리가 있는 서버가 뜨고 저장되는 것까지만 확인한다(좀비가 시야 밖에서 시작).
- 소음을 내는 실제 호출자(발소리, 전투)가 없어 "플레이어 행동 → 소음 → 좀비 반응"은 테스트에서 `emit`을 직접 부르는 형태로만 확인했다.
- 저장을 사이에 둔 틱 단위 재현(P2-31), 설정 상한보다 큰 좀비 수.

### 6.4 Phase 2-C에서 검증하지 못한 항목

- 네트워크: 전투 RPC가 없어 실제 클라이언트 요청 → 서버 판정 → 두 클라이언트가 같은 결과를 받는 흐름은 확인하지 못했다(N1, P2-Z). 요청 빈도 제한, 타입이 틀린 RPC 인자 검증도 N1 몫이다.
- 실제 서버 프로세스에서의 전투: 스모크 테스트는 전투 시스템이 등록된 서버가 뜨고 저장되는 것까지만 확인한다. 공격은 단위 테스트에서 `request_melee_attack`을 직접 불러 확인했다.
- 성능: 공격마다 모든 좀비와 모든 아이템(인벤토리 조회)을 훑는다. 좀비·아이템이 많을 때의 비용은 재지 않았다.
- 밸런스: 무기 수치는 플레이 테스트를 거치지 않았다.
- 좀비가 반격하는 실제 교전(좀비가 보고 물어뜯는 동안의 전투)은 전투 단위 테스트에서 격리했다(좀비 시야 0, 이동 속도 0). 좀비 쪽 반응은 좀비 테스트가 다룬다.

| P2-48 | 발소리 수치 (A3) **[사용자 확인 필요]** | 걸은 거리 2m마다 발소리 1번, 세기 8(소음 모델 P2-20 기준 방금 난 소리가 약 7m까지 들린다. 좀비 시야 25m보다 훨씬 짧아 "등 뒤 가까이 지나가면 들킨다" 정도), 주파수 이름 `broadband`. 걷기 한 종류뿐이라 달리기·웅크리기·바닥 재질·짐 무게에 따른 차이가 없다. 서버 이동 속도 4m/s에서는 플레이어 한 명이 초당 2번 소음을 내고, 소음 수명 8초 동안 약 16개가 살아 있다(소음 상한 256개, P2-23) | 발소리 세기·간격, 달리기/은신 자세별 세기(docs/02 §5.1 은신), 바닥 재질 |

| P2-50 | 이동 소음 저장 (A3) | 저장하지 않는다. 시스템 상태는 플레이어별 "마지막 발소리 이후 걸은 거리"(보폭 하나 미만)와 직전 위치뿐이고, 재시작 뒤에는 모두 오프라인이라 접속할 때 0에서 다시 시작한다. 잃는 것은 많아야 발소리 한 번이다. 소음 자체도 저장하지 않는다(P2-23) | 없음(지속 소음원이 생기면 P2-23과 함께 재검토) |

### 6.6 P2-A3에서 검증하지 못한 항목

- 실제 서버 프로세스: 클라이언트가 보낸 이동 의도 → 서버 이동 → 발소리 → 좀비 반응은 단위 테스트에서 `set_move_input`/`step_movement`/`step_systems`를 서버와 같은 순서로 직접 불러 확인했다. 실제 ENet 클라이언트로는 확인하지 않았다(스모크 테스트의 클라이언트는 움직이지 않는다).
- 성능: 걷는 플레이어가 많을 때 늘어나는 소음 수가 좀비 청각 조회 비용에 주는 영향, 소음 상한(256개)에서 오래된 소음이 밀려나는 상황은 재지 않았다.
- 월드 시간 배율이 1이 아닐 때: P2-T1에서 해소. 소음 수명이 행동 시간(실제 초)이 되어 배율과 무관하다. 배율 1과 24에서 발소리 수와 소음 만료 시점이 같음을 `time_axes_test.gd`가 비교한다.
- 밸런스: 세기 8·보폭 2m는 플레이 테스트를 거치지 않았다. 기존 좀비·전투·네트워크 테스트는 발소리가 켜진 기본 설정에서 수정 없이 통과했지만, 그 테스트들이 발소리가 좀비 행동을 바꾸는 상황을 다루는지는 따로 확인하지 않았다.

### 6.8 Phase 2-N1a에서 검증하지 못한 항목

- 실제 네트워크(다른 머신, 손실·지연·재정렬·NAT). 모든 테스트는 한 프로세스 안의 localhost ENet이다. 채널 0과 2 사이의 순서 뒤바뀜, 스냅샷 유실은 미러에 직접 값을 넣는 테스트로만 확인했다.
- 대역폭: P2-82의 localhost 일회성 측정뿐이다. 전투 중(이벤트가 많은 상황) 송신량과 실제 데이터그램 크기는 재지 않았다.
- 서버가 아닌 peer가 보낸 좀비 RPC의 실제 전송 경로: 엔진이 authority RPC를 핸들러 호출 전에 거부하면서 오류를 출력하고, 테스트 러너는 그 출력을 실패로 처리한다. 그래서 핸들러를 로컬에서 직접 호출하는 형태(발신 id 0)와 서버 역할에서의 호출만 테스트했다.
- 좀비 64마리 초과, 클라이언트 2명 초과, 장시간 실행.
- 실제 서버/클라이언트 프로세스에서의 미러 내용: 스모크 테스트는 12마리가 담긴 join 스냅샷으로 두 클라이언트가 접속하는 것까지만 확인한다. 화면 표시는 N2.

### 6.12 P2-N1c에서 검증하지 못한 항목

- 실제 별도 프로세스 스모크에서 생존 이벤트를 강제로 발생시키는 흐름은 없다. `NetTestCluster`의 실제 localhost ENet 서버 1 + 클라이언트 2/늦은 접속으로 검증했다.
- 256개 큐가 지속해서 넘치는 부하, 여러 플레이어의 출혈 피해가 매 틱 쌓이는 상황의 대역폭·CPU는 측정하지 않았다.
- 패킷 손실·장시간 지연·재접속 중 이벤트 유실은 별도 네트워크 에뮬레이션으로 확인하지 않았다. 재접속 시 현재 상태는 join fragment로 복구하지만 접속하지 않았던 동안의 최근 이벤트는 재생하지 않는다.
- 공개 범위는 P2-9 임시안 그대로이며 사용자/제품 정책 확인이 필요하다. 특히 파티원·의료 행동·관찰 거리별 추가 공개는 구현하지 않았다.

### 6.9 P2-N1b(전투 네트워크) 임시 가정 (PROVISIONAL)

이 티켓은 조정자가 배정한 P2-60~P2-69 범위를 쓴다(P2-66~P2-69는 비어 있다). 수치는 `data/tuning/combat_net_settings.tres`, 계약은 docs/09 §14.13에 있다.

| P2-60 | 근접 공격 요청 빈도 제한 (N1b) | peer별 토큰 버킷 4/s·버스트 4(줍기와 같은 값, P1-10). 맨손 쿨다운 0.8초 기준 정상 플레이는 초당 약 1.25회라 여유가 있다. 이 제한은 요청 트래픽만 막고 실제 공격 간격은 서버 쿨다운이 정한다. 형식이 틀린 요청은 토큰을 쓰지 않고 그대로 거부·기록한다(줍기와 같은 순서). 반복 위반 peer를 내보내는 처리는 없다 | 측정 후 수치 조정, 반복 위반 peer 처리(P1-10과 함께), 형식 오류 요청도 버킷에 포함할지 |

### 6.10 P2-N1b에서 검증하지 못한 항목

- 실제 네트워크: 모든 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다. 지연·손실·재전송이 있는 환경, 다른 머신 사이에서는 확인하지 않았다.
- 실제 서버·클라이언트 프로세스에서의 공격: 스모크 테스트의 클라이언트는 공격 요청을 보내지 않는다. 프로세스 3개 스모크는 모듈이 조립된 상태로 접속·종료가 되는 것까지만 확인한다.
- `BuildInfo.PROTOCOL_VERSION`은 N1 묶음 병합 때 3으로 올렸다. 버전이 다른 빌드의 접속 거절은 기존 `network_session_test`(프로토콜 불일치 거절)로만 확인했고, 실제 구버전 빌드와의 접속은 확인하지 않았다.
- 좀비 복제 모듈(다른 티켓)과 함께 돌렸을 때의 메시지 순서(`melee_attack`과 `zombie_damaged`/`zombie_died`, 좀비 스냅샷의 체력 비율과의 일치)는 확인하지 않았다. 이 브랜치에는 그 모듈이 없다. Phase 2 수용 시나리오(P2-Z)에서 확인해야 한다.
- 좀비가 반격하는 교전 중의 공격, 플레이어가 이동하면서 하는 공격: 테스트는 좀비 시야 0·속도 0, 발소리 끔, 생존 회복·리스폰 끔으로 격리했다.
- 성능·대역폭: 여러 플레이어가 동시에 연타할 때의 메시지 수·크기, 이벤트가 한 틱에 32개를 넘는 실제 부하는 재지 않았다(분할 전송은 메시지당 2개 설정으로 5개 이벤트까지만 확인).
- 서버 재시작을 사이에 둔 순번 초기화와 같은 클라이언트 프로세스의 재접속: 늦은 접속(새 클라이언트)만 확인했다.
- 엔진이 거부하는 경로(클라이언트가 보낸 서버 전용 RPC, 인자 수가 다른 요청)는 엔진이 오류로 보고하므로, 해당 테스트는 그 구간에서만 `Engine.print_error_messages`를 끄고 결과(아무것도 바뀌지 않음)를 확인한다. 엔진이 실제로 거부 오류를 낸다는 것은 개발 중 출력을 켜고 한 번 눈으로 확인했을 뿐 자동 검사에 들어 있지 않다.
- 클라이언트 표시: N2가 공격 결과와 전투 이벤트를 HUD에 연결했다. 휘두르기·피격 애니메이션은 아직 없다.

### 6.13 Phase 2 수용 시나리오(P2-Z)에서 검증하지 못한 항목

대상은 `tests/scenarios/phase2_acceptance_test.gd`(테스트 4개)다. 수용 기준과 단언의 대응은 docs/12 §6에 있다.

시나리오가 기본 튜닝 파일과 다르게 둔 값(새 Resource 객체에만 적용하고 캐시된 기본 설정은 고치지 않는다):

| 범위 | 값 | 이유 |
|---|---|---|
| 전체 | `zombie.dev_spawn_count` 12 → 0, 좀비는 테스트가 `spawn_zombie`로 배치 | 거리와 방향을 알고 있어야 "등 뒤 발소리"와 "시야"를 구분해 단언할 수 있다 |

이 시나리오로 해소된 이전 미검증 항목: §6.2·§6.4의 "두 클라이언트가 같은 좀비를 보고 같은 전투 결과를 받는 흐름", §6.4·§6.10의 "좀비가 반격하는 실제 교전 중의 공격", §6.6의 "실제 ENet 클라이언트의 이동 의도 → 서버 이동 → 발소리 → 좀비 반응", §6.10의 "`melee_attack`과 `zombie_damaged`/`zombie_died`의 도착 순서"(좀비 이벤트가 먼저 오고 두 클라이언트에서 섞이는 순서가 같다)와 "서버 재시작 뒤 전투 이벤트 순번이 1부터 다시 시작".

시나리오를 쓰다가 찾아 고친 결함:

- 좀비 공격 간격이 설정보다 한 판단 주기 길어지는 경우가 있었다. 월드 시각은 틱 길이를 더해 만든 값이라 "마지막 공격 시각 + 쿨다운"이 1.5초 뒤 판단 시점의 시계보다 부동소수 오차만큼 클 수 있고, 허용 오차 없이 비교해 그 판단을 "아직 이르다"로 처리했다. 기본값(쿨다운 1.5초, 판단 주기 0.5초, 60틱/초)에서 공격 간격이 1.5초가 아니라 2.0초가 되는 경우가 섞여 나왔다(P2-28의 "주기 단위 올림"과 다름. 재현 테스트의 20초 실행에서 고치기 전 간격 11개 중 5개, 틱 누적만 따로 계산하면 시작 틱의 약 57%). 선딜 0.5초도 같은 비교를 쓰므로 같은 이유로 늦어질 수 있다(선딜만 따로 재현하지는 않았다). `ZombieService`가 공격 가능 시각을 1e-6초 허용 오차로 비교하도록 고쳤다. 재현 테스트: `zombie_service_test.gd::test_attack_cooldown_is_not_stretched_by_float_accumulation`. 좀비의 다른 기한(`state_until`, `next_wander_at`, 시체 제거)과 전투 쿨다운(`CombatService`)은 같은 방식의 비교를 그대로 쓴다. 영향은 많아야 판단 주기 한 번(0.5초) 또는 서버 틱 한 번이라 고치지 않았다.

고치지 않고 남긴 관찰(결정 필요):

- 출혈 중인 플레이어는 서버 틱마다 `player_survival_damage` 이벤트를 하나씩 만든다. 교전 시나리오에서 한 명이 약 5.3초 출혈하는 동안 본인에게 간 생존 이벤트 320개 중 316개, 서버 INFO 로그 365줄 중 316줄이 이것이었다(틱당 reliable RPC 1개와 로그 1줄, 초당 60). §6.12의 "출혈 피해가 매 틱 쌓이는 상황"이 실제로 그렇게 동작한다는 확인이며, 묶어 보내는 주기는 정하지 않았다. **해결(P2-88)**: 이후 이 이벤트는 플레이어별로 설정 간격(기본 1 월드초)마다 합산해 한 번만 낸다(`survival_damage_events_test.gd`).
- 같은 이유로 `ClientSurvivalState.recent_events()`(128개 보관, P2-71)는 출혈 중 약 2초 분량만 담는다. 위 실행에서 교전이 끝났을 때 본인의 `player_infected`와 `player_wounded` 이벤트는 이미 목록에서 밀려나 있었다. `event_received` 시그널은 모두 전달되므로 시나리오는 시그널로 받았다. 표시 계층(N2)이 `recent_events()`를 주기적으로 읽어 알림을 만들면 물림·감염 알림을 놓칠 수 있다. P2-88 이후에는 출혈 이벤트가 초당 1개 수준이라 128개 보관으로 약 2분 분량이 남는다(실제 클라이언트로 다시 재지는 않았다).

검증하지 못한 항목:

- 실제 네트워크와 프로세스: 한 프로세스 안의 localhost ENet뿐이다. 프로세스 3개 스모크는 여전히 이동·공격을 보내지 않는다. 지연·손실·재정렬, 다른 머신은 확인하지 않았다.
- 기본 확률에서의 흐름: 긁힘, 감염 저항(`infection_exposure_resisted`), 긁힘으로 인한 감염은 수용 시나리오에 없다(통합·단위 테스트에만 있다).
- 플레이어 사망·리스폰이 낀 교전, 감염 말기 → 좀비화 사망: 시나리오의 플레이어는 죽지 않는다.
- 감염: 잠복·초기 두 단계의 시간만 확인했다. 진행·중증·말기 시간, 감염 경로별 시간 배율, 단계별 스태미나·체력 효과, 치료는 단위 테스트뿐이다.
- 부상 페널티: 물림 한 번(severity 0.3)인 한 점만 확인했다. 최소 배율, 여러 상처의 합산, 욕구 페널티와의 곱, 손·발 부위는 단위 테스트뿐이다.
- 좀비: 대상을 놓친 뒤 수색, 좀비 여러 마리가 같은 대상·같은 소음에 반응하는 교전, 공격 소음에 끌려오는 좀비는 수용 시나리오에 없다. 저장 시점에 남아 있는 좀비는 멀리 있는 `idle` 한 마리뿐이라 추격·공격 중인 좀비의 저장/복구는 확인하지 않았다.
- 전투: 이동하면서 하는 공격, 맨손과 무기가 섞인 교전, 스태미나 부족으로 거부되는 공격은 없다. 팔 부상 테스트는 전투 RNG(seed 0)의 처음 두 굴림을 테스트에서 다시 계산해 비교하므로 RNG 구현(엔진 PCG32)이 바뀌면 함께 바뀐다.
- 조작된 요청: 교전 중 4가지와 연타만 확인했다. 서버 전용 RPC를 클라이언트가 보내는 경우, 인자 수가 다른 요청은 엔진이 오류를 출력해 통합 테스트(`combat_net_test`, `zombie_net_test`)에서만 다룬다. 플레이어 ID를 인자로 받는 RPC가 없다는 것 자체는 `combat_net_test`가 고정한다.
- 재접속: 서버 재시작 뒤 새 클라이언트, 그리고 교전이 끝난 뒤 한 명이 나갔다 들어오는 경우만 확인했다. 좀비에게 공격받는 도중의 접속 종료·재접속, 교전 도중 늦은 접속은 수용 시나리오에 없다.
- 클라이언트 3명 이상, 좀비 3마리 이상, 긴 실행 시간. 시나리오는 P2-T1부터 기본 배율 24로 돈다(배율 1로는 더 이상 돌지 않는다).
- 표시 계층(N2): 미러와 시그널까지만 본다. 화면에 무엇이 보이는지는 확인하지 않는다.
- 성능·대역폭: 재지 않았다.
- 스태미나: 본인 미러의 스태미나는 초당 2회 스냅샷으로만 오므로 "스냅샷 두 주기 분량의 회복량 이내"로만 비교했다.
- 시간 의존: 대기는 조건 + 실제 시간 20초 한도다. 이 PC(headless 약 145fps)에서 `--filter=phase2` 연속 5회와 `tools/check.sh` 통과를 확인했다. 프레임이 0.5초 넘게 멈추는 환경에서는 좀비 배회 시작(스폰 3초 뒤부터) 전에 발소리를 듣게 하는 단계와 감염 단계 시각을 매 프레임 읽는 단계가 실패할 수 있다. P2-T1(기본 배율 24) 뒤에도 같은 PC에서 `--filter=phase2` 연속 5회(매번 4개 통과)와 `tools/check.sh` 통과를 확인했다. 감염 단계 테스트는 단계가 실제로 머무는 시간(0.6~1.8초)을 예전과 같게 두려고 설정값을 배율만큼 키웠다(위 표).

### 8.1 P2-N2에서 검증하지 못한 항목

- 실제 그래픽 창에서 캡슐 색·사망 자세·HUD 겹침과 여러 해상도/배율의 가독성을 눈으로 확인하지 못했다.
- 실제 마우스 입력이 별도 서버 프로세스까지 전달되어 승인/거부 결과와 전투/좀비 이벤트 로그가 함께 표시되는 흐름은 자동화하지 않았다. 공격 정책과 문자열 조립은 단위 테스트하고 기존 네트워크 통합 테스트에 의존한다.
- 많은 좀비/플레이어가 매 스냅샷마다 캡슐을 갱신할 때의 렌더링 비용과 이벤트가 빠르게 쌓일 때 HUD 갱신 비용을 측정하지 않았다.
- 보간·외삽이 없으므로 지연/손실 환경의 움직임 부드러움은 확인하지 않았다.

## 9. P2-T1 달력 시간·행동 시간 분리 임시 가정 (PROVISIONAL)

docs/00 ADR-006(게임 하루 = 실제 1시간, 배율은 달력 시간에만 적용)의 구현에서 정한 값이다. 계약은 docs/09 §14.16, 배율은 `data/tuning/world_clock_settings.tres`. 달력 시간 설정값(허기 48시간 등)은 이 티켓에서 바꾸지 않았다. **[사용자 확인 필요]** 표시는 제품 결정이라 사용자가 확정해야 한다.

| P2-100 | 두 시간 축과 일시정지 | 달력 시각 `world_time_sec`(실제 초 × `time_scale`, 기본 24)와 행동 시각 `action_time_sec`(실제 초)를 `WorldClock` 하나가 진행한다. 접속자 0명 일시정지 때는 둘이 함께 멈춘다. 행동 시각은 "월드가 돌아간 실제 초"이지 벽시계가 아니다 | 서버가 비어 있을 때의 진행 여부(docs/00 §8), 낮·밤 길이 |

1. (**→ P2-T8에서 대응 수단이 생겼다**: 누워 쉬면 피로가 준다. 최대에서 0까지 실제 20분, §12.3·§12.4. 아래는 P2-T8 이전의 서술이다.) 피로를 낮출 수단이 없다(수면 미구현). 접속 18분 뒤부터 스태미나 회복 ×0.75·이동 ×0.9, 약 34분 뒤부터 ×0.4·×0.6이 계속되고, "모든 욕구가 양호"가 깨져 자연 회복도 그때부터 영영 멈춘다. 지금은 죽어서 새 캐릭터로 시작해야만 풀린다(P2-T4부터 그때 소지품을 잃는다).
2. 먹기·마시기(P2-T3)가 들어오기 전에는 모든 캐릭터가 접속 약 1시간 7분 뒤 탈수로 죽는다(배율 1에서는 약 27시간이라 드러나지 않았다). P2-T3 뒤에는 새 월드에 음식 6단위·물 6단위가 놓인다(§11 P2-121). 다 먹으면 다시 같은 상황이 된다(아이템이 새로 생기는 규칙이 없다).
3. 물림 한 번이면 출혈만으로 약 26분 뒤 죽는다. 플레이어가 쓸 지혈 수단이 없다(`stop_bleeding`은 서버 seam뿐, P2-16). 출혈 중에는 자연 회복도 없다. **→ P2-T6에서 대응 수단이 생겼다**: 붕대 한 단위가 가장 심한 출혈 상처 하나를 지혈한다(§12.1, 소요 시간은 §12.4). 붕대가 없으면(새 월드에 3개, 다시 생기지 않음) 위 시간 그대로 죽는다.
4. 감염 치료 가능 구간은 감염 뒤 실제 20분인데 치료 아이템이 없다. 감염되면 약 1시간 35분 뒤 사망이 확정이다(P2-18). **→ P2-T7에서 대응 수단이 생겼다**: 치료제 한 단위가 초기 증상 단계까지의 감염을 해제한다(§12.2, 소요 시간은 §12.4). 20분을 넘기거나 치료제가 없으면(새 월드에 2개, 다시 생기지 않음) 위 시간 그대로 죽는다.
5. 자연 회복이 실제 3분 30초에 체력 전부, 긁힘 상처는 약 1분에 사라진다. 조건(욕구 전부 양호·출혈 없음)이 맞는 동안에는 전투 피해와 부상 페널티가 매우 빨리 없어진다.
6. 감염 체력 감소만으로는 죽지 않는다(합계 69). 말기 15분이 끝나는 순간 좀비화로 죽는다. 의도한 곡선인지 확인이 필요하다(P2-19).

### 9.2 P2-T1에서 검증하지 못한 항목

- 실제 서버 프로세스를 오래(실제 1시간 이상) 돌려 달력 규칙이 위 표대로 진행되는지 보지 않았다. 단위 테스트는 긴 틱이나 수십 초~수 분 분량의 실행이고, 수용 시나리오는 수십 초다.
- 배율 변경: 실행 중 변경은 구현이 없다. 저장을 사이에 두고 배율이 바뀌는 경우는 "배율 1로 만든 이전 저장을 배율 24로 읽는" 한 가지만 테스트했다.
- 배율이 1이 아니던 이전 저장(P2-102), 스키마 v1(Phase 1) 저장에 좀비가 있는 경우(Phase 1에는 좀비가 없어 해당 없음).
- 아주 긴 실행의 부동소수 정밀도: 실제 1,000시간이면 `world_time_sec`가 약 8.6e7이고 배정밀도 간격이 약 1.5e-8초라 문제가 없다고 계산만 했다.
- 성능: 틱당 추가 계산(생존의 축 환산)은 측정하지 않았다.
- 클라이언트 표시: `scripts/presentation/**`은 고치지 않았다. HUD가 `world_time`을 시간 계산에 쓰지 않는다는 것은 코드 검색으로만 확인했다.
- 프레임이 길게 멈추는 환경에서의 수용 시나리오: 이 PC에서의 반복 실행 결과는 §6.13에 적었다.

### 10.1 P2-T2에서 검증하지 못한 항목

- 실제 네트워크: 모든 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다. 지연·손실·재전송이 있는 환경, 다른 머신 사이에서는 확인하지 않았다.
- 실제 서버·클라이언트 프로세스에서의 내려놓기: 스모크 테스트의 클라이언트는 내려놓기 요청을 보내지 않는다. 프로세스 3개 스모크는 모듈이 조립된 상태로 접속·종료가 되는 것까지만 확인한다.
- 클라이언트 화면: 내려놓기 입력과 인벤토리 표시가 없다(`scripts/presentation/**`는 이 티켓 범위 밖). 미러(`ClientWorldState`)까지만 확인했다. 월드 아이템이 화면에 그려지는지는 확인하지 않았다.
- "같은 틱" 테스트의 범위: 서버가 네트워크를 읽지 않는 동안 두 클라이언트가 요청을 보내게 해서 한 번의 poll(같은 서버 틱)에 내려놓기·줍기·중복 내려놓기가 함께 처리되는 것을 확인했다. 두 요청 중 어느 쪽이 먼저 읽히는지는 전송 계층이 정하므로 회차마다 실제로 일어난 순서에 대해서만 검사한다(개발 중 실행에서는 두 순서가 모두 나왔지만, 매 실행에서 두 순서가 다 나온다는 보장은 테스트에 없다).
- 엔진이 거부하는 경로(클라이언트가 보낸 서버 전용 RPC, 인자 수가 다른 요청)는 엔진이 오류로 보고하므로, 해당 테스트는 그 구간에서만 `Engine.print_error_messages`를 끄고 결과(아무것도 바뀌지 않음)를 확인한다.
- 후속 티켓의 실제 호출: "전부 내려놓기"와 "제거"는 테스트가 `ServerWorld` 래퍼를 직접 불러 복제를 확인했다. 생존 시스템의 `step()` 안(사망 처리 도중)이나 다른 NetModule의 RPC 핸들러 안에서 부르는 경우는 P2-T3·P2-T4에서 확인해야 한다. 접속이 끊기는 도중(`leave` 훅)에 일어난 변화가 저장되는지도 확인하지 않았다.
- 오프라인 플레이어의 인벤토리 변화: 래퍼가 오프라인 플레이어에게도 동작하는 것은 단위 테스트로만 확인했고, 그 플레이어가 다시 접속해 스냅샷으로 받는 흐름은 네트워크 테스트에 없다.
- join 처리 도중(`ServerWorld.join`의 시스템 훅 안)에 일어난 인벤토리 변화: 그 peer에게 따로 보내지 않고 뒤이어 만드는 join 스냅샷에 들어간다는 것은 코드 순서로만 판단했고 테스트가 없다(지금은 그 시점에 인벤토리를 바꾸는 시스템이 없다).
- 성능·대역폭: 저장이 잦을 때(연속 내려놓기, 소비)의 저장 비용, 인벤토리가 큰 경우의 메시지 수·크기는 재지 않았다(분할 전송은 메시지당 2개 설정으로 4개까지만 확인).
- 버전이 다른 빌드의 접속 거절은 기존 `network_session_test`(프로토콜 불일치 거절)로만 확인했다. 실제 구버전(프로토콜 3) 빌드와의 접속은 확인하지 않았다.

#### P2-T3에서 검증하지 못한 항목

- 실제 네트워크와 프로세스: 모든 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다. 프로세스 3개 스모크의 클라이언트는 소비 요청을 보내지 않는다.
- 클라이언트 화면: 소비 키 입력에서 요청까지, HUD 라벨의 위치·겹침·가독성은 실제 창에서 확인하지 못했다. 선택 로직과 문구는 단위 테스트, 요청·결과·미러는 통합 테스트로만 확인했다. 월드에 놓인 아이템은 화면에 그려지지 않으므로(P2-T2에서도 같음) 플레이어는 음식이 어디 있는지 볼 수 없다. 줍기 키는 가장 가까운 아이템을 고를 뿐이다.
- 비정상 종료: 프로세스를 실제로 죽이지 않았다. "지금 서버가 죽으면 무엇이 복구되는가"는 실행 중에 디스크의 저장을 따로 읽어 확인했다.
- 24배속에서의 실제 플레이 시간(음식·물이 표의 시간만큼 버티게 하는지)은 계산만 했다. 테스트는 욕구가 스스로 변하지 않도록 증가 속도를 사실상 0으로 두었다.
- 저장 비용·대역폭은 재지 않았다.
- 구버전(프로토콜 4) 빌드와의 접속 거절은 기존 `network_session_test`(프로토콜 불일치 거절)로만 확인했다.

|---|---|---|---|
| P2-126 | 죽은 캐릭터의 소지품 **[사용자 확인 필요]** | 사망 순간(새 캐릭터 시작 때가 아니라) 들고 있던 것 전부를 죽은 위치 한 점에 내려놓는다. 묶음은 그대로, 사라지는 것 없음. 시체 컨테이너가 아니라 일반 월드 아이템이라 누구나(같은 플레이어의 새 캐릭터 포함) 주울 수 있고, 시간이 지나도 없어지지 않는다. 죽은 위치는 다른 플레이어에게 죽은 캐릭터의 캡슐과 아이템 위치로 드러난다. 빈손으로 죽으면 인벤토리 트랜잭션이 없어 그 틱에는 저장되지 않는다(사망 상태는 다음 저장에 들어간다) | 시체(컨테이너)로 남길지, 일부만 떨어뜨릴지, 소멸 시간, 자기 물건을 되찾는 것을 막을지, 사망 자체를 즉시 저장할지 |
| P2-127 | 새 캐릭터의 시작 **[사용자 확인 필요]** | 사망 뒤 `respawn_delay_sec`(기본 10 실제 초)이 지나면 자동으로 시작한다(플레이어의 확인 입력 없음). 위치는 고정 스폰 지점 한 곳, 빈 인벤토리, 체력·스태미나 최대, 욕구 0, 상처·감염 없음. 시작 소지품 없음(지급 트랜잭션이 없다, P2-119). 기한은 월드의 행동 시각 기준이라 죽은 채 접속을 끊어도 다른 플레이어가 접속해 있는 동안에는 지나가고(서버가 비면 시계와 함께 멈춘다), 판정은 본인이 접속해 있을 때만 한다: 기한 뒤 다시 접속하면 접속 직후 첫 틱에 시작한다(접속 스냅샷은 아직 죽은 상태). 새 캐릭터 시작은 따로 저장하지 않는다(다음 저장에 포함. 그 전에 서버가 죽으면 죽은 상태로 복구되어 같은 세대 번호로 다시 시작) | 대기 시간, 플레이어가 "새로 시작"을 눌러야 하는지, 스폰 위치(무작위·쉘터·선택), 시작 소지품과 초기 욕구, 캐릭터 만들기 화면. P2-T9에서 전용 서버는 "대기 시간 뒤 플레이어가 새 캐릭터를 만들어야 시작"으로 바뀌었고 캐릭터 만들기 화면이 생겼다(§13 P2-160, P2-167). 자동 시작은 캐릭터 생성이 필요 없는 조립(테스트·도구)에만 남아 있다 |
| P2-128 | 캐릭터 식별 **[사용자 확인 필요]** | 접속 신원 `player_id`와 인벤토리 컨테이너 ID는 죽어도 그대로다. 플레이어 상태에 `character_generation`(1부터, 새 캐릭터마다 +1, 저장됨, 플레이어 파일 스키마 v3)만 추가했다. `(player_id, character_generation)`이 캐릭터 하나를 가리킨다. 캐릭터별 이름·외형·기록(사망 원인, 생존 시간)은 없고, 지난 캐릭터의 정보는 남기지 않는다. 생존 fragment(체력·상처·감염)는 플레이어당 하나를 덮어쓴다. 이후 NPC 관계가 캐릭터에 붙으려면 이 쌍을 키로 쓰면 된다는 최소 장치일 뿐이다 | 캐릭터 전용 ID(UUID)·이름·외형, 지난 캐릭터 기록 보존, NPC가 새 캐릭터를 같은 사람으로 대하는지(Phase 4~5). P2-T9에서 캐릭터에 이름과 외형이 생겼다(플레이어 파일 스키마 v4의 `character`, docs/09 §14.24). 캐릭터 전용 ID와 지난 캐릭터의 기록은 여전히 없고, 새 캐릭터가 이전 캐릭터의 이름·외형을 덮어쓴다(§13 P2-178) |
| P2-129 | 죽은 캐릭터의 행동 제한 | 죽은 캐릭터는 아이템을 줍거나 내려놓거나 소비할 수 없다(`player_dead`). 줍기·내려놓기는 새 공통 훅 `ServerSystem.player_action_block_reason`을 `ServerWorld.try_pickup`/`try_drop_item`이 묻는 방식이라, 줍기 RPC의 결과 사유에 `player_dead`가 추가됐다(Phase 1 계약 확장, `network_service.gd`는 수정하지 않음). 넣은 이유: 이 검사가 없으면 죽은 플레이어가 대기 시간 동안 자기가 떨어뜨린 물건을 다시 주워 들 수 있고, 그대로 접속을 끊으면 그 물건이 죽은 캐릭터에 묶인다. 훅은 지금 아이템 행동에만 쓰인다(이동은 기존 이동 배율 0, 공격은 전투 규칙이 따로 거부) | 기절 등 다른 "행동 불가" 상태가 생길 때 이 훅으로 합칠지. P2-T8에서 수면이 이 훅을 쓴다(`player_resting`): 줍기·내려놓기에 더해 아이템 사용과 근접 공격도 이 훅을 묻게 됐다(§12.3 P2-152). 이동은 여전히 이동 배율로 막는다 |
| P2-130 | 다른 플레이어에게 보이는 것 | 기존 공개 이벤트 그대로다: `player_died`(원인 없음), `player_respawned`(위치). 새 캐릭터인지, 몇 번째 캐릭터인지는 본인에게만 보낸다(본인 스냅샷 `character_generation`). 다른 플레이어는 같은 `player_id`의 캡슐이 스폰 지점에 다시 나타나는 것으로 안다. 이벤트 이름 `player_respawned`은 복제 계약을 깨지 않으려고 그대로 두었다 | 새 캐릭터임을 다른 플레이어에게 알릴지(이름·외형이 생기면 자연히 드러남), 이벤트 이름 변경. P2-T9에서 이름과 외형은 모든 접속자에게 공개하고 세대 번호는 계속 본인에게만 보낸다(설정으로 공개 가능, §13 P2-168) |
| P2-131 | 이전 저장과의 호환 | 플레이어 파일 v2 → v3은 세대 1을 넣는다. P2-T4 이전 규칙으로 저장된 "소지품을 든 죽은 플레이어"는 그대로 로드하고 새 캐릭터가 시작될 때 그 자리에 떨어뜨린다(한 번). 생존 fragment v1의 죽은 플레이어가 접속 없이 다시 저장되면 다음 로드가 실패하던 결함(P2-T1 보고)은 로드 때 사망 시각을 채우도록 고쳤다 | 없음(이전 저장을 버려도 되면 안전망 삭제 가능) |

#### P2-T4에서 검증하지 못한 항목

- 실제 네트워크와 프로세스: 한 프로세스 안의 localhost ENet(`NetTestCluster`)뿐이다. 프로세스 3개 스모크의 플레이어는 죽지 않는다.
- 좀비에게 실제로 물려 죽는 흐름과 영구 사망의 결합: 통합 테스트는 서버에서 `apply_damage`를 직접 불러 죽였다. 좀비 공격(`ZombieService` → `apply_damage`)으로 죽는 경우 같은 경로를 타지만 좀비 AI가 도는 상태에서의 사망·소지품·새 캐릭터는 수용 시나리오에 없다(P2-Z의 플레이어는 죽지 않는다).
- 굶주림·탈수·출혈로 죽는 경우의 네트워크 흐름: 단위 테스트(탈수)만 있다.
- 비정상 종료: 프로세스를 실제로 죽이지 않았다. "새 캐릭터 시작 직후 저장 전에 서버가 죽는" 경우는 코드 경로로만 판단했다(죽은 상태의 저장을 로드해 새 캐릭터가 다시 시작되는 것은 테스트했다).
- 세 명 이상, 여러 명이 같은 틱에 죽는 경우, 인벤토리가 가득 찬(20칸) 캐릭터의 사망(메시지 분할은 P2-T2에서 4개까지만 확인).
- 접속 스냅샷이 "죽은 상태"로 간 직후 새 캐릭터가 시작되는 순간의 클라이언트 표시(캡슐이 죽은 자리에서 스폰 지점으로 순간이동).
- 클라이언트 화면: HUD의 "캐릭터 #N"과 사망 안내 문구는 문자열 조립만 단위 테스트했다. 실제 창에서 보지 못했다.
- 세대 번호의 상한: 정수라 사실상 없다고 보고 검사하지 않았다.

### 11.3 P2-T5 감염 사망 자리의 좀비

계약은 docs/09 §14.20. 수치는 `data/tuning/zombie_settings.tres`(`player_death_zombie_rule`, `max_active_zombies`).

| # | 항목 | 임시 가정(현재 구현) | 결정 필요 사항 |
|---|---|---|---|
| P2-132 | 어떤 사망이 좀비를 남기는가 **[사용자 확정 2026-11-15 → ADR-011: 기본값을 "감염 상태의 모든 사망"(`INFECTED_AT_DEATH`)으로 변경. 아래는 이전 임시안 설명]** | 설정 `player_death_zombie_rule`, 기본값 "감염이 사망 원인일 때": (1) 말기가 끝나 좀비화한 사망, (2) 감염 단계의 체력 감소가 사망에 들어간 경우(감염만으로, 또는 출혈·굶주림·탈수와 함께. 감염의 몫이 작아도 원인 문자열에 `infection`이 들어가면 해당). 기본값에서 좀비가 생기지 않는 경우: 비감염자의 모든 사망, **감염된 플레이어가 전투 피해(좀비의 공격 포함)로 죽은 경우**, 감염 초기(잠복·초기 단계는 체력 감소가 0)에 출혈·굶주림·탈수로 죽은 경우, 물려서 그 한 번에 죽은 비감염자(치명타에는 감염 판정이 없다). 다른 두 값: "생성 안 함", "감염된 상태의 모든 사망"(전투 사망 포함) | 감염된 채 다른 원인으로 죽은 플레이어도 좀비가 되는지(세계관: 감염자는 어떻게 죽든 되살아나는가), 물려 죽은 비감염자, 감염의 몫이 작은 복합 사망을 어떻게 볼지 |
| P2-133 | 좀비 수 상한 | 플레이어 좀비도 `max_active_zombies`(기본 64, 시체 포함)에 포함된다. 상한이면 생성을 생략하고 경고 로그(`player_id`, 사유 `zombie_limit`)와 서버 카운터만 남긴다. 나중에 다시 시도하지 않고, 다른 좀비를 지워 자리를 만들지도 않는다. 플레이어의 사망·소지품·새 캐릭터는 그대로 진행된다 | 플레이어 좀비는 상한과 무관하게 항상 생성할지, 오래된 시체를 먼저 지울지 |
| P2-134 | 플레이어 좀비의 모습과 능력 | 일반 좀비와 완전히 같다(체력 100, 같은 감지·속도·공격 수치, 같은 ID 계열). 죽은 플레이어의 위치와 바라보던 방향에서 `idle`로 시작하고 그 자리를 기준으로 배회한다. 플레이어의 외형·소지품·상처를 물려받지 않는다(소지품은 P2-T4대로 바닥에 놓인다). 어느 플레이어였는지는 좀비 상태에 저장하지 않는다(서버 로그에만 남는다). 생성 직후 주변 플레이어를 보면 일반 좀비처럼 추격·공격하고, 같은 플레이어의 새 캐릭터도 공격 대상이다 | 플레이어였던 좀비의 차별점(외형, 능력, 소지품을 지니고 다니는지), 누구였는지를 저장할지(기념물·퀘스트·NPC 반응에 필요해지면) |
| P2-135 | 다른 플레이어에게 보이는 것 **[사용자 확인 필요]** | 좀비 이벤트와 스냅샷에는 플레이어 ID가 없고, 공개 `player_died`에는 여전히 원인이 없다. 즉 "이 좀비는 A였다"는 메시지는 없다. 그러나 죽은 캐릭터가 있는 자리에 같은 순간 좀비가 나타나므로, 그것을 보는(지금은 거리 제한 없이 모든) 플레이어는 A가 감염으로 죽었음을 추론할 수 있다. ADR-009는 감염 여부를 본인만 알게 하지만, ADR-008의 결과(좀비가 생김)는 관찰 가능한 사실이라 숨기지 않았다. 살아 있는 동안의 감염 여부·단계는 계속 비공개다 | 죽음과 좀비 등장 사이에 시간차를 둘지(곧바로 드러나지 않게), 플레이어였던 좀비임을 명시적으로 알릴지, 관심 영역(거리) 필터 |
| P2-136 | 결합 방식과 시점 | 생존 시스템은 `player_died` 시그널만 내고 좀비 시스템을 모른다. 연결은 `ServerComposition.create_world` 한 곳이다. 좀비는 사망과 같은 서버 틱에 생긴다(좀비 시스템이 자기 `step` 중이면 그 `step`이 끝날 때). 저장은 따로 일으키지 않는다: 죽은 플레이어가 소지품을 들고 있었으면 그 틱 끝의 저장에 함께 들어가고, 아니면 다음 저장에 들어간다(그 전에 서버가 죽으면 감염된 채 살아 있던 저장으로 돌아가 다시 죽고 좀비가 다시 하나 생긴다) | 사망을 즉시 저장할지(P2-126과 함께), 다른 시스템(사건 원장, NPC 반응)이 같은 시그널을 쓰게 될 때의 순서 규칙 |

#### P2-T5에서 검증하지 못한 항목

- 실제 네트워크와 프로세스: 한 프로세스 안의 localhost ENet(`NetTestCluster`)뿐이다.
- 살아 움직이는 좀비와의 결합: 테스트의 좀비는 시야·청각·이동을 끈 상태다(미러를 정확히 비교하기 위해서다). 새로 생긴 좀비가 주변 플레이어나 같은 플레이어의 새 캐릭터를 실제로 추격·공격하는 흐름은 확인하지 않았다(일반 좀비와 같은 코드라 기존 좀비 테스트에 의존한다).
- 좀비에게 물려 감염된 뒤 기본 설정 시간(실제 약 1시간 35분)으로 진행해 좀비화하는 전체 흐름: 테스트는 감염을 서버에서 직접 걸고 단계 시간을 줄였다.
- "감염된 상태의 모든 사망" 규칙의 네트워크 흐름, 상한에 걸린 경우의 네트워크 흐름: 단위 테스트뿐이다.
- 여러 플레이어가 같은 틱에 감염으로 죽는 경우, 좀비가 많은 상태(상한 근처)에서의 성능.
- 클라이언트 화면: 좀비 캡슐이 죽은 플레이어 캡슐과 같은 자리에 겹쳐 보이는 모습은 실제 창에서 확인하지 못했다.

### 11.4 사용자 확인이 필요한 결정 모음 (P2-T3~T5)

위 표에서 **[사용자 확인 필요]**로 표시한 항목을 한곳에 모은다. 모두 설정값이나 가장 단순한 규칙으로만 구현했다.

1. 음식·물의 수치: 개발용 식량 허기 −40, 물 갈증 −50, 최대 스택 5(P2-120).
2. 먹는 규칙: 즉시 적용, 욕구가 0이어도 소비됨(낭비 가능), 먹는 시간·제한 없음(P2-122). **[사용자 확정 2026-11-15 → ADR-013 현재 구현 유지]**
3. 다른 플레이어에게 "먹었다"를 보이지 않음(P2-124).
4. 죽은 캐릭터의 소지품: 사망 즉시 전부 죽은 자리에, 일반 월드 아이템으로, 사라지지 않음, 같은 플레이어의 새 캐릭터도 주울 수 있음(P2-126). **[사용자 확정 2026-11-15 → ADR-012 새 캐릭터도 주울 수 있음, 현재 구현 유지]**
5. 새 캐릭터: 10초 뒤 자동 시작, 고정 스폰 지점, 욕구 0, 시작 소지품 없음(P2-127, P2-17).
6. 캐릭터 식별: `player_id` 유지 + 세대 번호만. 이름·외형·지난 캐릭터 기록 없음(P2-128). **[사용자 확정 2026-11-15 → ADR-015 이름·외형 커스터마이징 추가, P2-T9]**
7. 좀비를 남기는 사망의 범위(P2-132): **[사용자 확정 2026-11-15 → ADR-011]** 감염된 상태의 모든 사망이 좀비를 남긴다(기본 규칙을 `INFECTED_AT_DEATH`로 변경). 이전 임시안은 "감염이 사망 원인일 때만"이었다.
8. 플레이어 좀비의 정체: 메시지로는 알리지 않지만 죽은 자리에 바로 나타나 추론 가능(P2-135).

## 12. P2-T6~T8 붕대, 치료제, 수면 임시 가정 (PROVISIONAL)

사용자 결정(2026-11-15): 24배속에서 드러난 "대응 수단이 없는 위협" 셋(§9.1의 1·3·4번)에 붕대(지혈), 치료제(감염 초기 치료), 수면(피로 감소)을 추가한다. 수치는 사용자가 정하지 않았으므로 전부 설정값·아이템 정의 데이터이고 확정이 아니다. 이 절은 P2-140~P2-159 범위를 쓴다. **[사용자 확인 필요]** 표시는 제품 결정이라 사용자가 확정해야 한다.

#### P2-T6에서 검증하지 못한 항목

- 실제 네트워크와 프로세스: 모든 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다. 프로세스 3개 스모크의 클라이언트는 아이템을 쓰지 않는다.
- 클라이언트 화면: 키 입력에서 요청까지, HUD 줄의 위치·겹침·가독성은 실제 창에서 확인하지 못했다(이 환경은 headless다). 줄이 늘어나 생존 HUD 라벨과 인벤토리 라벨의 세로 위치를 100px씩 옮겼는데(`client_view.tscn`) 눈으로 보지 못했다. 선택 로직·문구·키 등록은 단위 테스트, 요청·결과·미러는 통합 테스트로만 확인했다.
- 좀비에게 실제로 물려 출혈하는 흐름에서의 붕대 사용: 테스트는 서버에서 `apply_damage`를 직접 불러 상처를 냈다. 좀비 공격도 같은 `apply_damage`를 쓰지만 좀비 AI가 도는 상태에서 붕대를 쓰는 수용 시나리오는 없다.
- 24배속에서의 실제 플레이 시간(§12.4의 표)은 설정값으로 계산만 했다. 테스트는 배율 1 시계에서 출혈 피해가 멈추는 것을 확인했다.
- 붕대 사용 직후 저장 전에 서버가 죽는 경우: 프로세스를 실제로 죽이지 않았다. 실행 중에 디스크의 저장을 따로 읽어 "붕대가 아직 묶음에 있다"만 확인했다.
- 상처가 상한(64개)에 걸려 목록에 없는 피해, 붕대 한 단위가 여러 곳을 지혈하는 정의의 네트워크 흐름(단위 테스트뿐).

계약은 docs/09 §14.22. 수치는 `resources/definitions/items/dev_cure.tres`, `data/tuning/dev_world_seed.tres`, `data/tuning/survival_settings.tres`(`infection_treatment_max_stage`), `data/tuning/client_presentation_settings.tres`.

| P2-149 | 정보 공개와 다른 플레이어 치료 **[사용자 확인 필요]** | 다른 플레이어는 감염·치료·거부에 대해 아무것도 받지 않는다(ADR-009 그대로). 자기 자신에게만 쓸 수 있다: 감염된 동료에게 치료제를 써 줄 수 없고, 줄 수 있는 방법은 내려놓아 줍게 하는 것뿐이다(내려놓기 입력은 클라이언트에 아직 없다, P2-T2). 다른 플레이어를 치료하게 하려면 대상의 감염 여부가 치료하는 쪽에 드러나는지(성공/거부 사유)가 ADR-009와 부딪히므로 함께 정해야 한다 | 다른 플레이어 치료 허용 여부와 그때의 정보 공개(시도하면 감염 여부가 드러남), 치료제를 건네는 UI |

#### P2-T7에서 검증하지 못한 항목

- 실제 네트워크와 프로세스: 모든 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다.
- 좀비에게 실제로 물려 감염된 뒤 치료하는 흐름: 테스트는 서버에서 `apply_infection_exposure`를 직접 불렀고(감염 확률 1), 통합 테스트의 "너무 늦은 단계"는 서버의 감염 단계를 직접 바꿔 만들었다(단계 시간을 사실상 멈춘 설정). 단위 테스트는 단계 시간을 1시간으로 줄여 시간 경과로 각 단계에 도달시켰다. 기본 설정 시간(잠복 2시간·초기 6시간)으로 치료 창이 실제 20분인지는 계산만 했다.
- 치료 직후 저장 전에 서버가 죽는 경우: 프로세스를 실제로 죽이지 않았다. 실행 중에 디스크의 저장을 따로 읽어 확인했다.
- 클라이언트 화면: 치료제 키 입력에서 요청까지, HUD 둘째 치료 줄의 배치는 실제 창에서 확인하지 못했다.
- 치료와 좀비화가 같은 틱에 겹치는 경우(말기 끝 직전의 요청): 말기는 어차피 치료 불가라 해당 없고, 초기 → 진행 경계에서의 요청은 서버 틱 순서(생존 규칙 `step` → 네트워크 요청 처리)대로 "그 틱의 단계"로 판정된다는 것을 코드로만 확인했다.

#### P2-T8에서 검증하지 못한 항목

- 실제 네트워크와 프로세스: 모든 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다. 프로세스 3개 스모크의 클라이언트는 눕지 않는다.
- 클라이언트 화면: 휴식 키 입력에서 요청까지, HUD 줄, 누운 캡슐의 모습(기울기·높이·색)은 실제 창에서 확인하지 못했다. 자세 계산과 문구는 단위 테스트, 요청·결과·미러는 통합 테스트로만 확인했다. 키 R이 이동·줍기 키와 겹치지 않는다는 것은 기본값을 눈으로 대조했을 뿐 설정 검증에는 없다(P2-144와 같다).
- 기본 수치로 실제 20분을 누워 피로가 최대에서 0이 되는지는 계산만 했다. 테스트는 배율 1에서 월드 1시간, 배율 24에서 실제 25~60초 분량이고, 통합 테스트는 회복 시간을 약 3초로 줄였다.
- 좀비와의 결합: 통합 테스트는 좀비 한 마리를 누운 플레이어 1m 앞에 놓고 첫 공격으로 깨는 것까지 확인했다. 기본 월드의 좀비 12마리(스폰 지점에서 40~90m)가 배회하다 누운 플레이어를 실제로 발견하는 빈도, 여러 마리가 동시에 공격하는 경우는 보지 않았다.
- 좀비 공격으로 깨는 같은 틱에 일어나기 요청이 도착하는 경우(요청은 `not_resting`으로 거부된다는 것을 코드로만 확인), 같은 틱에 눕기 요청과 피격이 겹치는 순서.
- 세 명 이상이 동시에 눕는 경우의 메시지 양, 관심 영역 없이 모든 접속자에게 보내는 비용은 재지 않았다.
- 긴 휴식 중 접속이 끊겼다가 돌아오는 흐름은 "퇴장 → 재접속하면 서 있다"만 확인했다. 재접속 뒤 다시 눕는 것까지는 확인했다.

| 자다가 허기로 깸(P2-T10) | 위험 범주 75 | 허기 0에서 누우면 1시간 30분 뒤. 허기 68.3 이상에서 누우면 8분 안에 깬다 |
| 출혈 중에 잠(P2-T10) | 체력 30 이하에서 기상 | 물림 1회(체력 85, 초당 0.054)면 약 17분 뒤 체력 30에서 깬다(8분 수면은 다 잔다: 체력 약 59). 심한 열상(체력 50, 초당 0.24)이면 약 83초 뒤 깬다. 깬 뒤 붕대가 없으면 깨어 있는 채 죽는다 |
| 감염된 채로 잠(P2-T10) | 말기 진입 시 기상 | 물린 뒤 1시간 20분(잠복 5분 + 초기 15분 + 진행 30분 + 중증 30분)에 깨고, 그 뒤 15분(말기) 동안은 누울 수 없다 |
| 자는 중 피격(P2-T10) | 최소 체력 1 | 기본 수치에서는 걸리지 않는다(자는 플레이어의 체력 > 30, 좀비의 한 대 ≤ 15) |

생존 루프 요약(기본 설정, 한 명 기준, 계산값. 휴식 수치는 P2-T10 기준): 새 캐릭터는 18분 뒤 피로 주의, 24분 뒤 갈증 주의, 48분 뒤 허기 주의가 된다. 세 욕구를 양호로 두려면(자연 회복의 조건) 갈증이 주의에 닿기 전인 24분마다 물 한 병(−50, 30분어치라 10은 남는다), 48분마다 식량 한 개(−40, 꼭 48분어치), 18분마다 약 3분의 휴식이 필요하다(피로를 주의까지 두지 않고 한 번에 몰아 자면 45분 활동 뒤 8분). 주의 구간을 감수하고 물을 30분마다 마시면 낭비가 없다. 물리면 붕대와 치료제를 각각 하나씩 20분 안에 써야 한다. 새 월드의 물 6병은 2시간 24분~3시간, 식량 6개는 약 4시간 48분 분량이고 붕대 3개·치료제 2개와 함께 다시 생기지 않는다(P2-121, P2-142, P2-148).

### 12.5 사용자 확인이 필요한 결정 모음 (P2-T6~T8)

위 표에서 **[사용자 확인 필요]**로 표시한 항목을 한곳에 모은다. 모두 설정값이나 가장 단순한 규칙으로만 구현했다.

1. 붕대의 효과: 한 단위가 가장 심한 출혈 상처 1곳을 즉시 지혈. 상처는 남고 체력은 돌려주지 않음. 최대 스택 5(P2-140).
2. 붕대 사용 규칙: 출혈이 없으면 거부되고 소비되지 않음(먹기와 다름). 자기 자신에게만, 상처 선택 없음(P2-141). **→ 사용자 결정으로 변경(P2-T12): 가까운 다른 플레이어에게도 쓸 수 있음. §14.3.**
3. 붕대 사용을 다른 플레이어에게 보이지 않음(P2-143).
4. 사용 키: 음식 F, 물 G, 붕대 B(치료제 V는 P2-T7). F의 뜻이 "첫 소비 가능 아이템"에서 "음식"으로 바뀜(P2-144).
5. 치료제의 효과: 한 단위로 즉시 완치, 모든 치료제가 같은 단계(초기 증상)까지 들음, 면역 없음, 품질·실패·의료 능력 없음(P2-146, P2-18).
6. 치료제 사용 규칙: 감염되지 않았거나 너무 늦었으면 거부되고 소비되지 않음. 지금은 본인이 잠복기에도 감염 사실을 알기 때문에 정보 누출이 아니지만, 잠복기를 본인에게 숨기기로 하면 이 규칙을 "항상 소비"로 바꿔야 함(P2-147, ADR-009).
7. 자기 자신만 치료 가능. 다른 플레이어를 치료하게 하면 시도 결과로 상대의 감염 여부가 드러남(P2-149, ADR-009). **→ 사용자 결정으로 변경(P2-T12): 다른 플레이어를 치료할 수 있고, 결과로 상대의 감염 여부가 치료하는 쪽에 드러나는 것을 감수함. §14.3 P2-198.**
8. 피로 회복 속도: 최대에서 0까지 월드 8시간 = 실제 20분. 피로를 양호로 유지하려면 플레이 시간의 약 31%를 누워 있어야 함. 다 쉬어도 자동으로 일어나지 않음(P2-150). **→ 사용자 결정으로 변경(P2-T10): 월드 3.2시간 = 실제 8분, 약 15%. §14.1 P2-180.**
9. 쉬는 동안 허기·갈증은 깨어 있을 때와 같이 오르고, 출혈·굶주림·탈수로는 깨지 않아 누운 채 죽을 수 있음(P2-151, P2-153). **→ 사용자 결정으로 변경(P2-T10): 위험해지면 깨고 누운 채 죽지 않음. §14.1 P2-182~P2-185.**
10. 쉬는 중에는 이동·공격뿐 아니라 줍기·내려놓기·먹기·붕대·치료제도 불가. 먼저 일어나야 함(P2-152).
11. 좀비는 누운 플레이어를 서 있는 플레이어와 똑같이 보고 공격함. 첫 공격이 깨움(P2-156). **→ 사용자 결정으로 변경: 그 첫 공격으로는 죽지 않음(P2-T10, §14.1 P2-185), 자는 플레이어는 조금 덜 보임(P2-T11, §14.2).**
12. "누워 있음"은 거리 제한 없이 모든 접속자에게 공개. 피로와 일어난 원인은 본인만(P2-157).
13. 키 배치: 휴식 R(눕기/일어나기 겸용)(P2-155).

| P2-175 | 저장 형식과 이전 저장 | 플레이어 파일 v4(`character`). v3 → v4는 기본 이름과 빈 외형(읽을 때 기본값으로 채움)을 넣어, 이전 저장의 플레이어는 생성 없이 바로 들어온다. 외형 데이터가 바뀌면 없어진 항목은 버리고 없어진 선택지는 기본값으로 바꿔 읽는다(경고 로그). 이름 규칙이 바뀌어도 저장된 이름은 그대로 둔다 | 이전 저장의 플레이어에게 다음 접속 때 생성 화면을 띄울지 |
| P2-176 | 서버와 클라이언트의 외형 데이터 | 같은 빌드면 같다고 가정한다. 접속 때 데이터가 같은지 확인하지 않는다. 클라이언트는 자기 데이터로 완전하지 않은 캐릭터 행을 버리고(그 플레이어는 이름 없는 기본 캡슐로 보인다), 서버는 모르는 선택지를 거부한다 | 접속 핸드셰이크에서 외형 데이터 해시를 비교할지, 서버가 정의를 내려보낼지(모드 지원) |
| P2-177 | 이름의 유니코드 처리 | 정규화하지 않는다. 분해된 자모(NFD)로 들어온 한글은 허용 범위 밖이라 거부된다. 중복 비교와 금칙어 비교는 `to_lower()`만 쓴다. 모양이 비슷한 다른 문자(동형 문자)는 허용 범위를 좁게 두는 것으로만 막는다 | 정규화(NFC) 도입, 다른 언어를 허용할 때의 혼동 문자 처리 |
| P2-178 | 지난 캐릭터의 기록 | 남기지 않는다. 새 캐릭터를 만들면 이전 캐릭터의 이름·외형은 덮어써진다(P2-128과 같다). 월드에 놓인 소지품에는 누구 것이었는지 표시가 없다 | 지난 캐릭터 기록(이름, 사망 원인, 생존 시간), 묘비·시체 |
| P2-179 | 생성 화면의 구성 | 이름 칸, 항목마다 이전/다음 버튼(목록·미리보기 없음), 색 항목의 색 견본, 무작위 버튼(외형만 바꾸고 이름은 그대로), 만들기 버튼, 거부 사유 한 줄. 캐릭터 미리보기는 없다. 다시 열리면 지난번 이름과 선택이 남아 있다. 취소 버튼은 없다(만들지 않으면 플레이할 수 없다) | 미리보기, 목록형 선택, 무작위 이름, 서버에서 나가기 버튼 |

#### P2-T9에서 검증하지 못한 항목

- 실제 창: 생성 화면의 배치, 한글 글꼴(시스템 글꼴 대체에 의존), 이름표의 크기와 가독성, 마우스 캡처가 풀리고 다시 잡히는 것, 이름 칸의 키 입력을 보지 못했다. 모든 UI 테스트는 headless에서 노드와 시그널로만 확인했다.
- 한글 입력기(IME): 조합 중 Enter, 조합 중인 글자와 `max_length`의 관계.
- 생성 화면이 떠 있는 동안의 입력 차단: `ClientView.is_game_input_enabled()` 값만 확인했다. 실제 키·마우스 입력으로는 확인하지 않았다.
- 실제 네트워크와 다른 머신: 통합 테스트는 한 프로세스 안의 localhost ENet, 스모크는 같은 PC의 프로세스 3개다. 한글 실행 인자(`--character-name=스모크 B`)는 이 PC(Windows, Git Bash)에서만 확인했다.
- 생성 필수 모드에서의 전체 교전 시나리오: Phase 2 수용 시나리오는 호환 기본값으로 돈다. 생성 필수 모드는 "캐릭터 없는 플레이어를 좀비가 무시한다"(단위)와 생성·사망·재생성의 복제(통합)로 나눠 확인했다.
- 서버와 클라이언트의 외형 데이터가 실제로 다른 경우: 미러가 행을 버리는 것만 단위로 확인했다.
- 여러 명이 같은 순간에 같은 이름을 요청하는 경우(중복 금지 설정): 서버가 요청을 하나씩 처리하므로 먼저 처리된 쪽이 얻는다고 판단했고, 순서대로 요청한 경우만 테스트했다.
- 4명 초과, 긴 이름(16자) 여러 개가 겹쳐 보이는 화면, 이름표가 벽에 가려지는 경우(벽이 아직 없다).
- 비정상 종료: 프로세스를 실제로 죽이지 않았다. "생성 직후 저장"은 저장 세대가 늘고 플레이어 파일에 이름이 있는 것으로 확인했다.
- 캐릭터 없는 접속자가 오래 머물며 자리를 차지하는 경우의 운영 영향.

### 13.1 사용자 확인이 필요한 결정 모음 (P2-T9)

위 표에서 **[사용자 확인 필요]**로 표시한 항목을 한곳에 모은다. 모두 설정값·데이터나 가장 단순한 규칙으로만 구현했다.

1. 외형 항목과 선택지: 체형 6, 키 7, 피부색 8, 머리 모양 9, 머리색 9, 상의 색 12, 하의 색 10. 성별·얼굴 등은 없음. 색은 팔레트에서만 고름(P2-163, P2-161).
2. 이름 규칙: 2~16자, 한글 음절·영문·숫자·공백만. 문장 부호와 "ㅋㅋ" 같은 자모, 다른 언어, 이모지는 거부(P2-164).
3. 같은 이름을 여러 캐릭터가 쓸 수 있음. 금칙어 목록은 비어 있음. 이름을 정한 적 없는 캐릭터의 이름은 "생존자"(P2-165).
4. 죽은 뒤에는 대기 시간(10초)이 지나고 플레이어가 새 캐릭터를 만들어야 시작함. 만들 때까지 시간 제한이 없고 죽은 캐릭터가 월드에 남음(P2-167).
5. 세대 번호(그 플레이어의 몇 번째 캐릭터인지)는 본인에게만 알림. 다른 플레이어에게는 이름과 외형만 보임(P2-168).
6. 만든 뒤에는 이름·외형을 바꿀 수 없음(P2-166).
7. 캐릭터를 만들기 전의 접속자는 다른 사람에게 전혀 보이지 않고, 생성 화면에 머무는 시간 제한이 없음(P2-169).
8. 이전 저장의 플레이어는 "생존자"와 기본 외형으로 바로 들어옴(생성 화면이 뜨지 않음)(P2-175).

## 14. P2-T10~T12 수면 조정, 엎드리기와 은신, 다른 플레이어 치료 임시 가정 (PROVISIONAL)

사용자 결정(2026-11-15, 붕대·치료제·수면을 보고받은 뒤. 원문): "수면시간 좀 줄이자 피로도 높으면 작업도 능력치가 떨어지고", "자는 중 사망은 빼고 위험지수일 때 깨도록, 공격받으면 데미지 입지만, 즉사는 아니에", "엎드리면 은신효과는 있지만, 자는건 없게, 그래도 움직이는것보다는 적게", "남 치료도 가능하게". 결정 기록은 docs/00 ADR-016~018. 방향은 사용자가 정했고 수치와 세부 규칙은 정하지 않았으므로 전부 설정값·데이터이며 확정이 아니다. 이 절은 P2-180~P2-199 범위를 쓴다(뒤에 이어진 P2-T13은 P2-200, P2-T14 건네기는 §14.5의 P2-205~P2-212). **[사용자 확인 필요]** 표시는 제품 결정이라 사용자가 확정해야 한다.

#### P2-T10에서 검증하지 못한 항목

- 실제 네트워크와 프로세스: 통합 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다. 프로세스 3개 스모크의 클라이언트는 눕지 않는다.
- 기본 수치로 실제 8분을 누워 피로가 최대에서 0이 되는지는 계산과 "기본값 × 60 ÷ 배율 = 8분" 단언뿐이다. 서버를 8분 돌려 재지 않았다. §12.4의 새 행(갈증·허기·출혈·감염으로 깨는 시각)도 설정값으로 계산한 값이다.
- 통합 테스트의 위험 기상은 갈증 한 가지다(갈증 증가를 빠르게 한 설정). 허기·체력·감염 기상의 복제는 같은 이벤트 경로라 단위 테스트로만 확인했다.
- 자는 중 피격 하한의 통합 테스트는 좀비 피해를 10만으로 올린 설정이다. 기본 수치에서는 하한이 걸리는 상황 자체가 없다.
- 좀비 두 마리 이상이 같은 틱에 자는 플레이어를 치는 경우는 `apply_damage`를 연속 호출하는 단위 테스트로만 확인했다(실제 좀비 두 마리 배치는 하지 않았다).
- 깨는 틱에 눕기·일어나기 요청이 함께 도착하는 순서(서버 틱은 생존 `step` → 네트워크 요청 처리 순서라 요청은 깬 뒤의 상태로 판정된다는 것을 코드로만 확인).
- 클라이언트 화면: 피로 문구 줄, 기상 알림, 거부 문장이 실제 창에서 어떻게 보이는지 확인하지 못했다(headless). HUD 줄이 하나 늘 수 있어 라벨 높이가 넘치는지도 보지 못했다. 문구와 "본인 이벤트만 알림"은 단위 테스트로 확인했다.
- 피로 페널티가 실제 전투 흐름(좀비를 몇 대에 잡는가)에 주는 영향은 재지 않았다. 피해 값이 배율만큼 줄어드는 것만 확인했다.
- 설정을 바꾼 조합(체력 기준을 높게, 욕구 기상을 끔, 감염 기상 단계를 앞당김) 중 테스트한 것은 "욕구 기상 끔"과 "감염 기상 끔"뿐이다.

- 실제 네트워크와 프로세스: 통합 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다. 프로세스 3개 스모크의 클라이언트는 엎드리지 않는다.
- 클라이언트 화면: 엎드리기 키 입력에서 요청까지, 자세 HUD 줄, 엎드린 캡슐의 모습(앞으로 기운 각도·높이·이름표 위치)은 실제 창에서 확인하지 못했다(headless). 기울기·높이 계산과 문구, 키 등록은 단위 테스트로만 확인했다. 키 C가 이동·줍기 키와 겹치지 않는다는 것은 기본값을 눈으로 대조했을 뿐 설정 검증에는 없다(P2-144와 같다). HUD 줄이 하나 늘어 라벨이 화면 밖으로 넘치는지 보지 못했다.
- 기본 수치(시야 25m)에서의 좀비 감지: 단위·통합 테스트는 시야 20m 설정에서 자세별 경계의 안팎 0.5m를 확인했다. 기본 월드의 좀비 12마리가 배회하는 상황에서 엎드려 지나가기가 실제로 얼마나 쓸 만한지(체감)는 재지 않았다.
- 좀비의 시야각 가장자리, 여러 좀비가 같은 플레이어를 서로 다른 상태(한 마리는 추격, 한 마리는 대기)로 보는 경우는 "추격 중인 좀비 한 마리"와 "보고 있지 않던 좀비 한 마리"를 따로 테스트했을 뿐 함께 두지는 않았다.
- 엎드려 기는 소리로 좀비가 조사하러 오는 흐름: 발소리의 세기·수·들리는 거리만 확인했고, 그 소리를 들은 좀비의 반응은 기존 청각 테스트에 맡겼다(소리가 작아졌다는 것 외에 달라진 것이 없다).
- 움직임 기억 시간(0.5초)과 좀비 판단 주기의 맞물림: 걷다가 멈춘 직후의 판단이 "움직이는 중"으로 보는 것은 확인했지만, 주기를 바꾼 설정 조합은 보지 않았다.
- 접속 직후 첫 서버 틱 전의 플레이어는 가시성 1.0이다(자세 시스템이 아직 위치를 보지 못함). 실제로는 한 틱(1/60초)이라 영향이 없다고 판단했고 따로 테스트하지 않았다(통합 테스트를 쓰다가 드러나 대기 조건을 고쳤다).
- 세 명 이상이 동시에 자세를 바꾸는 경우의 메시지 양, 관심 영역 없이 모든 접속자에게 보내는 비용은 재지 않았다.
- 통합 테스트(`posture_net_test.gd`)는 서버 규칙과 모듈을 구현한 뒤에 작성했다. 구현 전에 실패하는 것을 확인한 것은 단위 테스트(`posture_test.gd`: 빈 껍데기 `PostureService`에 대해 15개 중 13개가 동작 단언에서 실패)와 화면 문구 테스트다.

| P2-198 | 정보 공개 **[사용자 확인 필요]** | 치료하는 쪽: 결과 사유만 받는다. 그것으로 붕대는 상대의 출혈 여부를, 치료제는 상대의 감염 여부와 "치료 가능 단계를 지났는지"를 알게 된다(사용자가 감수하기로 한 범위). 체력·상처 목록·단계 이름·남은 출혈 수는 받지 않는다. 대상: 누가 어떤 아이템을 썼고 효과가 있었는지 받는다(효과가 없었던 시도도). 제3자: "A가 B를 돌봤다"는 공개 알림만 받고, 아이템 종류·성공 여부·B의 상태는 받지 않는다. 공개 알림은 성공한 치료와 "치료할 것이 없어 거부된 시도" 모두에 보내므로 제3자는 둘을 구분하지 못한다(성공만 알리면 치료제 성공이 곧 "B는 감염자였다"가 된다). 거리 제한 없이 모든 접속자에게 간다. **남는 누출 경로**: 치료하는 쪽이 붕대·치료제를 한 개씩 들고 다니며 여러 사람에게 "써 보는" 것으로 감염자를 찾아낼 수 있다(거부되면 아이템이 남으므로 비용이 없다). 그리고 제3자도 A의 인벤토리는 못 보지만 A가 말해 주면 안다 | 감염 여부가 드러나는 것을 줄일지: (가) 치료제는 대상의 감염과 무관하게 항상 소비되고 결과를 알리지 않는다, (나) 대상이 동의해야 한다, (다) 지금처럼 둔다. 제3자에게 아이템 종류(붕대인지 주사인지)를 보일지, 공개 알림의 거리 제한 |
| P2-199 | 의도·빈도·조작 | 새 의도는 소비 의도에 대상 인자 하나를 더한 별도 RPC이고(기존 소비 의도는 그대로), 대상이 비면 자기 사용이다. 빈도 제한은 소비 의도와 **같은 버킷**(기본 4/s·버스트 4)이다. 요청 번호는 따로 센다. 클라이언트의 대상 후보는 "카메라 방향 반각 60도, 2.5m 안의 가장 가까운 살아 있는 다른 플레이어"(미러 기준)이고 서버 판정과 다를 수 있다(미러가 늦으면 `target_too_far`로 거부된다). 조작은 Shift + 붕대(B)·치료제(V) 키. HUD에 후보 이름을 항상 표시한다. 대상을 목록에서 고르는 UI는 없다 | 대상 선택 UI(조준점, 목록), 키 배치, 후보 표시 방식(이름표 강조 등), 측정 후 빈도 조정 |
| P2-200 | 음식·물을 남에게 주는 방식(P2-T13, ADR-019) **[사용자 확인 필요]** | "먹여 주기"다: 주는 쪽의 한 단위가 줄고 받는 쪽의 허기·갈증이 바로 내려간다. 아이템이 받는 쪽 인벤토리로 옮겨 가지 않는다(받는 쪽이 나중에 먹으려고 보관할 수 없다). 아이템 자체를 넘기는 "건네기"는 P2-T14에서 따로 추가됐다(ADR-020, §14.5: Ctrl+사용 키, 받는 쪽 인벤토리로 옮겨 간다). 먹여 주기는 그대로 남아 있다. 사거리·대상 조건은 치료와 같다(2.5m, 살아 있고 월드에 있는 플레이어, 동의 없음, 자는 대상도 깨지 않음). 받는 쪽의 허기·갈증이 0이어도 수락되고 소비된다(자기 사용과 같다, ADR-013): 그래서 음식·물의 결과로는 받는 쪽의 상태를 알 수 없다. 조작은 Shift+음식(F)·물(G). 다른 접속자에게 가는 알림은 치료와 같은 "A가 B를 돌봤다"이고 무엇을 줬는지는 없다 | (건네기는 사용자 결정으로 P2-T14에서 추가됨: §14.5.) 받는 쪽이 배부를 때 거부할지, 받는 쪽의 동의, 제3자 알림에서 치료와 식사를 구분할지 |

#### P2-T12에서 검증하지 못한 항목

- 실제 네트워크와 프로세스: 통합 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다. 프로세스 3개 스모크의 클라이언트는 아이템을 쓰지 않는다.
- 클라이언트 화면과 입력: Shift를 누른 채 B·V를 눌렀을 때 실제로 "남에게 쓰기"로 처리되는지(보조 키 액션과 사용 키 액션이 함께 눌린 상태의 입력 처리), HUD의 치료 대상 줄, 이벤트 로그의 알림 문구는 실제 창에서 확인하지 못했다(headless). 후보 선택 로직·문구·키 등록은 단위 테스트, 요청·결과·알림은 통합 테스트로만 확인했다. `ClientView`가 후보를 매 물리 프레임 다시 고르는 비용은 재지 않았다(접속자 수에 비례하는 단순 순회다). HUD 줄이 또 하나 늘어 라벨이 넘치는지 보지 못했다.
- 클라이언트 후보와 서버 판정의 차이: 미러 위치가 늦어 후보로 고른 대상이 서버에서는 사거리 밖인 경우는 "서버가 `target_too_far`로 거부한다"를 서버 위치를 직접 옮겨 확인했을 뿐, 실제로 움직이는 두 플레이어로는 확인하지 않았다.
- 좀비에게 실제로 물린 동료를 치료하는 흐름: 테스트는 서버에서 `apply_damage`·`apply_infection_exposure`를 직접 불러 상처와 감염을 만들었다(§12.1·§12.2와 같다).
- 음식을 남에게 주는 설정(`allow_feeding_others`)은 P2-T12에서는 단위 테스트뿐이었다. P2-T13에서 기본값을 켜면서 네트워크 흐름과 정보 공개(주는 쪽은 결과만, 받는 쪽은 누가 무엇을 줬는지, 제3자는 "돌봤다"만)를 `treat_other_net_test.gd::test_a_client_gives_food_and_water_to_another_player`로 확인했다. 실제 창에서 Shift+F·G 입력과 문구는 확인하지 못했다(headless).
- 치료 직후 저장 전에 서버가 죽는 경우(먹기와 같은 방침이라 따로 확인하지 않았다), `save_after_consume`을 켠 경우의 남에게 쓰기.
- 네 명 이상, 여러 명이 같은 틱에 같은 대상을 치료하는 경우(서버가 요청을 하나씩 처리하므로 먼저 온 쪽이 치료하고 나중 쪽은 `not_bleeding` 등으로 거부된다고 판단했고, 순서대로 요청한 경우만 테스트했다).
- 통합 테스트(`treat_other_net_test.gd`)는 서버 규칙과 모듈을 구현한 뒤에 작성했다. 구현 전에 실패하는 것을 확인한 것은 단위 테스트(`treat_other_test.gd` 12개 전부, `treat_target_test.gd` 5개 전부가 동작 단언에서 실패)다.

### 14.4 사용자 확인이 필요한 결정 모음 (P2-T10~T12)

위 표들에서 **[사용자 확인 필요]**로 표시한 항목을 한곳에 모은다. 모두 설정값이나 가장 단순한 규칙으로만 구현했다.

P2-T10 수면 조정:

1. 수면 시간: 피로 최대 → 0이 실제 8분(P2-180).
2. 피로의 작업 능력 페널티: 주의 ×0.85, 위험 ×0.6, 지금은 근접 피해에만 적용(P2-181).
3. 자다가 깨는 조건: 허기·갈증이 위험 범주(75), 체력 30% 이하. 같은 상태에서는 누울 수 없음. 그래서 체력이 30% 이하인 중상자는 잠을 잘 수 없음(P2-182, P2-183).
4. 감염: 말기에 들어서면 깨고 말기에는 누울 수 없음. 좀비화는 자는지와 무관하게 일어남(P2-184).
5. 자는 중 피격: 그 한 대는 체력을 1 아래로 내리지 않음. 깬 직후의 보호 시간은 없어 다음 공격이나 출혈로 죽을 수 있음(P2-185).

P2-T11 엎드리기와 은신:

6. 가시성 배율: 서서 움직임 1.0, 서서 정지 0.9, 누워 잠 0.8, 엎드려 이동 0.6, 엎드려 정지 0.4(좀비 시야 25m 기준 25 / 22.5 / 20 / 15 / 10m)(P2-189).
7. 엎드린 상태: 이동 속도 35%, 발소리가 들리는 거리 7m → 2.2m, 근접 공격 불가, 아이템 사용·줍기는 가능, 자세 전환은 즉시(P2-190).
8. 좀비가 이미 보고 있는 앞에서 엎드려서는 추격을 끊을 수 없음. 시야 밖으로 벗어나 놓친 뒤에야 엎드림이 효과를 냄(P2-192).
9. 자세는 거리 제한 없이 모든 접속자에게 보임(다른 플레이어에게는 숨지 않음). 본인에게도 "들켰는지"는 알려 주지 않음. 키는 C(P2-194).

P2-T12 다른 플레이어 치료:

10. 남에게 쓸 수 있는 것은 붕대·치료제와 음식·물(음식·물은 2026-11-15 사용자 확정, ADR-019). 사거리 2.5m(P2-195, P2-196).
11. 대상의 동의 없이 치료함. 자는·엎드린 동료도 치료할 수 있고 치료받아도 깨지 않음(P2-197).
12. 치료하는 쪽은 결과로 상대의 출혈 여부(붕대)와 감염 여부·치료 가능 단계를 지났는지(치료제)를 알게 됨. 대상은 누가 무엇을 썼는지 앎. 옆에서 본 사람은 "A가 B를 돌봤다"만 알고, 성공한 치료와 치료할 것이 없었던 시도를 구분하지 못함(P2-198).
13. 조작: Shift를 누른 채 붕대(B)·치료제(V) 키 = 바라보는 방향의 가장 가까운 플레이어에게 사용(P2-199). P2-T13부터 음식(F)·물(G) 키도 같다.
14. 음식·물을 남에게 주는 것(Shift+키)은 "먹여 주기"(받는 쪽의 허기·갈증이 바로 내려감)임(P2-200). 아이템을 상대 인벤토리로 넘기는 "건네기"는 사용자 결정("건네기도 추가")으로 P2-T14에서 따로 추가됐고, 확인이 필요한 세부는 §14.5에 모았다.

### 14.5 P2-T14 아이템 건네기

사용자 결정(2026-11-15, 음식·물 먹여 주기를 보고받은 뒤. 원문): "건네기도 추가". 결정 기록은 docs/00 ADR-020, 계약은 docs/09 §14.28, 화면은 docs/11 §2.12. 방향(아이템 자체가 상대 인벤토리로 옮겨 가고 상대가 보관한다)은 사용자가 정했고 수치와 세부 규칙은 정하지 않았으므로, 전부 설정값이거나 가장 단순한 규칙이며 확정이 아니다. 수치는 `data/tuning/gameplay_settings.tres`(`hand_over_range_m`), `data/tuning/inventory_net_settings.tres`(내려놓기 의도의 빈도를 함께 쓴다), `data/tuning/client_presentation_settings.tres`(`hand_over_modifier_key`, `hand_over_quantity`). 이 절은 P2-205~P2-212 범위를 쓴다.

#### P2-T14에서 검증하지 못한 항목

- 실제 네트워크와 프로세스: 통합 테스트는 한 프로세스 안의 localhost ENet(`NetTestCluster`)이다. 프로세스 3개 스모크의 클라이언트는 아무것도 건네지 않는다.
- 클라이언트 화면과 입력: Ctrl을 누른 채 F·G·B·V를 눌렀을 때 실제로 건네기로 처리되는지(보조 키 액션과 사용 키 액션이 함께 눌린 상태의 입력 처리), Shift와 Ctrl을 함께 눌렀을 때, 길어진 HUD 대상 줄이 화면 너비 안에 들어가는지, 이벤트 로그의 알림 문구는 실제 창에서 확인하지 못했다(headless). `ClientView`의 입력 분기 자체(`_request_use`의 건네기 가지와 시그널 연결)에는 자동 테스트가 없다: 그 안에서 부르는 순수 함수(`ConsumeIntentPolicy.use_mode`·`hand_over_quantity`), 문구, 키 등록, 모듈의 요청·결과·알림만 테스트했다. Ctrl 조합이 운영체제나 창 관리자의 단축키와 겹치는지도 보지 못했다.
- 클라이언트 후보와 서버 판정의 차이: 미러 위치가 늦어 후보로 고른 대상이 서버에서는 사거리 밖인 경우는 서버 위치를 직접 옮겨 `target_too_far`를 확인했을 뿐, 실제로 움직이는 두 플레이어로는 확인하지 않았다.
- 같은 틱의 경합: 두 사람이 같은 틱에 한 받는 쪽의 마지막 빈 칸으로 건네는 경우, A→B와 B→A가 엇갈리는 경우, 건네는 순간 받는 쪽이 줍는 경우. 서버가 요청을 하나씩 처리하므로 먼저 온 쪽이 들어가고 나중 쪽은 `target_inventory_full` 등으로 거부된다고 판단했고, 순서대로 요청한 경우만 테스트했다.
- 받는 쪽이 건네는 순간 접속을 끊거나 join 도중인 경우: 받는 쪽이 온라인이 아니면 `target_unavailable`로 거부되고, 확정 뒤 소유자 메시지를 보낼 peer가 없으면 다음 join 스냅샷에 반영된다는 것은 코드로만 확인했다.
- 저장: 건네기 직후 저장 세대가 오른 것과 서버 재시작 뒤 두 인벤토리가 복구되는 것은 확인했다. 저장 자체가 실패했을 때(디스크 오류)는 줍기·내려놓기와 같은 경로라 따로 보지 않았다(오류 로그만 남고 결과는 승인으로 간다). 프로토콜 8 시절에 쓴 실제 저장 파일을 읽어 보지는 않았다(저장 스키마가 그대로라 마이그레이션이 없다는 판단뿐이다).
- 메시지 양: 받는 쪽 묶음 여러 개가 한 번에 채워지면 묶음마다 `_rpc_inventory_item_changed`가 하나씩 간다. 기본 데이터(`max_stack` ≤ 5, 한 번에 1개)에서는 하나이고, 테스트에서 본 최대는 둘이다. 칸 수를 크게 늘린 설정에서의 메시지 수·크기는 재지 않았다.
- 빈도: 기본값(4/s·버스트 4)에서 0.25초 간격 연타가 걸리지 않는지는 계산뿐이다. 테스트는 넉넉한 설정과 극단 설정(0.01/s·버스트 2) 둘이다.
- `condition`·`quality`가 다른 묶음을 합치지 않는 것은 단위 테스트에서 값을 직접 바꿔 확인했다(게임 안에서 값이 달라지는 경로가 아직 없다).
- 네 명 이상, 여러 명이 같은 틱에 서로 건네는 경우.
- 테스트 작성 순서: 구현 전에 실패하는 것을 확인한 것은 `tests/unit/hand_over_test.gd`(빈 껍데기 `transfer_item`·`try_hand_over_item`에 대해 그때 있던 18개 중 17개가 동작 단언에서 실패. 통과한 1개는 설정·사유 코드 테스트로, 그 데이터는 껍데기 단계에서 이미 넣었다)와 `tests/unit/hand_over_presentation_test.gd`(빈 껍데기에 대해 5개 전부 실패)다. `tests/integration/hand_over_net_test.gd` 전체, 그리고 `hand_over_test.gd`의 "슬롯 번호 순으로 채움" 테스트와 "건네받은 파이프가 무기가 됨" 단언은 구현 뒤에 작성했고 실패하는 것을 보지 않았다.

#### 사용자 확인이 필요한 결정 모음 (P2-T14)

1. 건네기 사거리 2.5m, 건네는 데 걸리는 시간 없음(P2-205).
2. 음식·물만이 아니라 모든 아이템을 건넬 수 있음. 무기를 건네면 바로 받은 쪽의 무기가 됨(P2-206).
3. 받는 쪽의 같은 종류 묶음에 먼저 합치고 남으면 빈 칸 하나에 넣음. 다 들어가지 않으면 일부만 건네지 않고 전체를 거부함. 줍기와 달리 건네기만 합침(P2-207).
4. 받는 쪽의 동의 없이 건넴. 자는·엎드린 동료도 받고 깨지 않음. 원하지 않는 아이템으로 남의 칸을 채울 수 있고, 받은 쪽이 버릴 입력(내려놓기 키)은 아직 없음(P2-209).
5. 건넨 쪽은 "상대의 소지품이 가득 찼는지"를 알게 됨. 받는 쪽은 누가 무엇을 몇 개 건넸는지 앎. 다른 접속자는 거리와 관계없이 "A가 B에게 무언가를 건넸다"만 앎. 실패한 건네기는 받는 쪽도 모름(P2-210).
6. 조작: Ctrl을 누른 채 음식(F)·물(G)·붕대(B)·치료제(V) 키, 한 번에 한 개. Shift와 함께 누르면 건네기. 네 종류에 속하지 않는 아이템을 건넬 입력은 없음(P2-211).
7. 건네기마다 바로 저장하고, 빈도 제한은 내려놓기와 합쳐 초당 4번(P2-208).
