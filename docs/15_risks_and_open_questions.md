# 15. 위험 요소 및 미결정 사항

## 1. 주요 위험

| 위험 | 영향 | 완화 |
|---|---|---|
| 기능 범위 과대 | 개발 지연/품질 저하 | vertical slice, MVP 제한 |
| NPC 수 증가 | 서버 AI 부하 | 계층형 시뮬레이션, 중앙 스케줄러 |
| 대규모 월드 | 메모리/렌더링/내비게이션 부하 | 구역 스트리밍, 프로파일링 |
| 멀티플레이 동기화 | 상태 불일치/치트 | 서버 권한, RPC 검증 |
| 동적 건축 | navmesh 갱신 비용 | 구역/타일 단위 갱신 실험 |
| 복잡한 관계 AI | 예측 불가/테스트 어려움 | 이벤트 기록, 결정론 seed, 디버그 도구 |
| 저장 데이터 복잡성 | 세이브 손상/마이그레이션 | 스키마 버전, 백업, 원자적 저장 |
| 시뮬레이션 오프라인 진행 | 플레이어 부재 중 과도한 손실 | 서버 옵션 및 계산 상한 |
| 비밀 정보 멀티플레이 | 클라이언트 정보 누출 | 플레이어별 knowledge projection |
| AI 행동의 부적절한 묘사 | 편향/낙인 | 정신적 고통과 폭력 원인을 단순 연결하지 않음 |

## 2. 미결정 질문

아래 항목은 후속 기획에서 결정해야 한다. Claude Code는 개발을 막지 않는 임시 가정을 명시하고, 임의로 제품 정책을 확정하지 않는다.

### 제품/플레이
- 최종 최대 동시 플레이어 수는 몇 명인가?
- 공개 서버와 개인 서버 중 어떤 것을 우선 제공할 것인가?
- 플레이어 사망 후 같은 캐릭터로 복귀 가능한가?
- 캐릭터 사망/좀비화 여부는 서버별로 조절할 것인가?
- PvP 및 플레이어 절도는 허용할 것인가?

### 월드
- 4km × 4km 후보 크기가 적절한가?
- 월드가 절차 생성인가, 수작업 맵인가, 혼합인가?
- 서버가 비어 있어도 작물/부패/감염이 진행되는가?
- 지역별 자원 재생성은 있는가?

### NPC/사회
- 서버당 NPC 최대 수는 얼마인가?
- NPC 수용/영입 제한은 쉘터 크기/식량/침대와 연동하는가?
- 연애는 독점 관계를 기본으로 할 것인가?
- NPC의 성인 관계/가족/출산 콘텐츠는 어디까지 포함할 것인가?
- 배신/살인 같은 중대 행동의 빈도와 금지 조건은 무엇인가?
- NPC 개인 비밀을 다른 플레이어에게 얼마나 공개할 것인가?

### 세계관/동물
- 감염 가능한 동물의 최종 종 목록은 무엇인가?
- 동물 감염은 물림만 가능한가, 혈액/체액도 가능한가?
- 치료제는 감염 후 어느 단계까지 효과가 있는가?

### 운영/배포
- 계정/친구 초대/서버 브라우저가 필요한가?
- 모드와 사용자 제작 콘텐츠를 지원할 것인가?
- 서버 관리 명령/백업/관리자 도구는 어떤 범위인가?

## 3. 미결정 항목 처리 규칙

- 구현이 가능한 경우 설정값/인터페이스만 먼저 만든다.
- 제품 정책과 밸런스를 하드코딩하지 않는다.
- 추후 변경 비용이 큰 항목은 ADR로 결정한다.
- 가정으로 진행한 경우 코드 주석과 문서에 `PROVISIONAL`을 표시한다.

## 4. Phase 0 부트스트랩 임시 가정 (PROVISIONAL)

Phase 0 구현 중 문서에 근거가 없어 개발을 막지 않는 범위에서 임시로 정한 사항이다. 모두 **확정이 아니며**, 변경 비용이 커지기 전에 검토/ADR이 필요하다.

| # | 항목 | 임시 가정(현재 구현) | 결정 필요 사항 |
|---|---|---|---|
| P0-1 | 테스트 프레임워크 | 외부 의존성 없는 자체 headless 러너(`tests/run_tests.gd`, `TestCase`). GUT 등은 Godot 4.7.2 호환성을 검증하지 못해 도입하지 않음. | 자체 러너 유지 vs GUT/GdUnit4 도입. 도입 시 4.7.2 호환 버전 고정과 기존 테스트 이전 방법. |
| P0-2 | 서버/클라이언트 역할 선택 | 같은 메인 씬에서 `-- --server`/`-- --client` 인자, 없으면 `dedicated_server` feature tag면 서버, 그 외 클라이언트. `--headless`만으로는 서버로 간주하지 않음. | 역할 선택 방식과 전용 서버 전용 진입 씬 분리 여부. |
| P0-3 | 전용 서버 export 플랫폼 | `export_presets.cfg`에 "Linux Dedicated Server"(x86_64) 프리셋을 둠. | 서버 공식 지원 OS(Linux/Windows), 배포 방식(docs/00 §8의 "전용 서버 배포 방식"과 연동). |
| P0-4 | 클라이언트 export 플랫폼 | "Windows Client"(x86_64) 프리셋만 둠(docs/00 "Windows PC 우선" 임시값 반영). | Linux/macOS 클라이언트 지원 여부. |

| P0-7 | 로그 형식/출력 | `<UTC ISO8601>Z [LEVEL] [subsystem] message \| key=value ...` 형식으로 stdout(ERROR/FATAL은 stderr). 키 이름에 password/token/secret/auth/credential이 포함되면 값을 마스킹. 파일 로깅은 Godot 기본 설정을 그대로 사용. | 서버 로그 파일 위치/로테이션/보존 기간, 구조화(JSON) 로그 필요 여부. |
| P0-8 | 렌더러 | Forward+ (`rendering/renderer/rendering_method`). | 저사양 PC 대상 여부(Mobile/Compatibility 렌더러 병행) — 세미 리얼리즘 목표와 최소 사양 결정 필요. |

### 4.1 Phase 0에서 검증하지 못한 항목

- 실제 GPU 렌더링 창에서 클라이언트 실행(검증 환경에 디스플레이 없음; 클라이언트는 headless 디스플레이 드라이버로만 실행 확인).
- export template를 사용한 실제 실행 파일 export(템플릿 미설치). `--export-pack`으로 만든 `.pck`를 에디터 바이너리로 실행하는 것까지만 확인.
- dedicated server export 시 `dedicated_server` feature tag에 의한 자동 서버 역할 선택(단위 테스트로 파서 로직만 검증).
- Windows 환경에서의 실행.

## 5. Phase 1 네트워크/플레이어 임시 가정 (PROVISIONAL)

Phase 1 구현에서 문서에 근거가 없어 **조정 가능한 설정값/인터페이스로만** 둔 사항이다. 모두 확정이 아니다.

| # | 항목 | 임시 가정(현재 구현) | 결정 필요 사항 |
|---|---|---|---|
| P1-1 | 플레이어 식별/인증 | 인증·계정 없음. 클라이언트가 `--player-key=<영숫자_- 1~64자>`를 보내고 서버가 `player_key → player_id`로 같은 플레이어를 찾는다. 키를 알면 누구나 그 플레이어로 접속할 수 있다(보안 없음). 키는 저장 데이터(world_state.json, players/*.json)에 평문으로 남는다. | 인증 방식(서버 암호, 토큰, 플랫폼 계정 등)과 신원 저장 방식. docs/00 §8 "서버 목록/초대/암호/관리 도구"와 연동. |
| P1-2 | 엔티티 ID 형식 | `<kind>_<6자리 이상 순번>`(예: `item_000042`), 다음 순번과 삭제 ID tombstone을 world_state에 저장. | UUID 전환 여부(docs/14 §1은 "UUID 또는 안정적인 문자열 ID"). 여러 서버/월드 병합 계획이 있으면 UUID 권장. |
| P1-3 | 프로토콜/게임/저장 버전 관계 | `BuildInfo.PROTOCOL_VERSION`(=1)이 정확히 일치해야 접속 허용. 게임 버전(`0.0.1`)은 로그만 남긴다. 저장 문서는 종류별 `schema_version`(item/player/world=1, manifest=1). | 버전 호환 정책(하위 호환 허용 범위, 업데이트 강제 방식). |
| P1-4 | 포트/인원/바인드 | `data/tuning/network_settings.tres`: port 24680, max_players 4(docs/00 초기 1~4 검증 목표), bind `*`, ENet 연결 여유분 +2(가득 찬 서버가 `server_full`을 응답하기 위함). `--port=`로 덮어쓰기 가능. | 기본 포트, 최대 인원, 서버 권장 사양. |
| P1-5 | 핸드셰이크/거절 | 접속 후 5초 안에 join 요청이 없으면 `handshake_timeout`, 거절 사유 전송 후 0.25초 뒤 연결 종료. 거절 코드: `protocol_mismatch`, `bad_type`, `bad_player_key`, `server_full`, `player_key_in_use`. | 거절 사유 표시(UI)와 재시도 정책. |
| P1-6 | 개발용 월드 내용 | 새 월드에는 `data/tuning/dev_world_seed.tres`의 `dev_test_item` 1개를 (6, 0, 0), 셀 `cell_0_0`에 배치. 셀 스트리밍 전까지 모든 월드 아이템의 location_id는 `cell_0_0`. | Phase 3 월드/루팅 생성 규칙으로 교체. |
| P1-7 | 월드 아이템 위치 저장 | `schemas/item_instance.schema.json`에 좌표 필드가 없어, 월드에 놓인 아이템의 좌표는 world_state의 `inventory.world_item_positions`(item_id → [x,y,z])에 따로 저장. | 스키마에 위치(transform) 필드를 추가할지, 셀 파일로 옮길지(docs/10 §3 cells/). |
| P1-8 | 이동 규칙/튜닝 | 충돌·물리 없음. 서버가 `move_speed_mps`=4.0, 월드 경계 ±250m(docs/00 500m×500m 테스트 맵)로 적분. 클라이언트는 방향(길이 ≤ 1)과 yaw(|yaw| ≤ 2π)만 전송. 입력 0.5초 무수신 시 정지(패킷 손실 대비), 정상 정지는 클라이언트가 ZERO 방향 전송. | 이동 속도/달리기/스태미나(Phase 2), 충돌·지형(Phase 3), 클라이언트 예측/보간(P1-4 이후). |
| P1-9 | 메시지 채널/신뢰성 | ch0 reliable ordered: join/거절/입퇴장/줍기/인벤토리. ch1 unreliable ordered: 이동 의도, 위치 스냅샷(20Hz, tick 번호로 오래된 것 폐기). docs/08 §7 "측정 후 선택"에 따라 측정 전 임시값. | 네트워크 프로파일링 후 채널/전송 모드/스냅샷 주기 확정. |
| P1-10 | 요청 빈도 제한 | 토큰 버킷: 이동 60/s(버스트 30), 줍기 4/s(버스트 4). | 측정 후 조정. 반복 위반 peer 처리(경고/추방) 정책. |
| P1-11 | 줍기 규칙 | 서버 위치 기준 거리 ≤ `pickup_range_m`(2.5m), 인벤토리 슬롯 20개(스택 단위), 먼저 승인된 요청만 성공. 무게/부피 없음. | 인벤토리 용량 모델(무게/부피/장비 슬롯), 상호작용 시간. |
| P1-12 | 저장 시점/보존 | 새 월드 생성 시, 줍기 성공 직후, 플레이어 퇴장 시, 서버 종료 시, 60초 주기 autosave에 전체 월드를 저장. 이전 세대 백업 3개 보존. 저장 루트 `user://saves`(`--save-root=user://...`로 변경 가능). | 저장 주기와 데이터 손실 허용 범위(docs/10 §5: 테스트로 결정), 증분 저장 필요 여부. |
| P1-13 | 저장 원자성 범위 | 파일별 임시 파일 → 검증 → 백업 → rename. 여러 파일 rename 도중 프로세스가 죽으면 파일 간 세대가 섞일 수 있고, 이 경우 직전 세대가 backups/에 남는다(자동 세대 일치 복구는 아직 없음). | manifest 기준 세대 일관성 검사/자동 롤백 도입 여부. |
| P1-14 | 플레이어 상태 범위 | PlayerState는 player_id, player_key, position, yaw, inventory_id, last_saved_at_utc만 저장(docs/14의 health/needs/infection 등은 Phase 2). 월드 시간(WorldClock)이 없어 저장 시각은 UTC로 별도 필드. | WorldClock 도입 후 `last_saved_at`(월드 시간) 추가. |
| P1-15 | 동시 접속 시 월드 시간 | 월드 시간 자체가 아직 없음(docs/00 "마지막 플레이어 퇴장 시 일시정지" 제안은 미구현). | WorldClock 티켓에서 결정. |

### 5.1 Phase 1에서 검증하지 못한 항목

- 실제 네트워크(다른 머신, 지연/손실/NAT) 환경. 모든 테스트는 localhost ENet.
- 클라이언트 렌더링 창에서의 이동 표시와 입력(카메라/입력은 P1-4로 별도).
- 장시간(soak) 서버 실행, 메모리/대역폭 측정, 4명 초과 부하.
- 저장 도중 프로세스 강제 종료(kill -9) 시 복구 — 단위 테스트는 손상 파일 복구까지만 검증.

### 6.1 Phase 2-A(소음·좀비) 임시 가정 (PROVISIONAL)

P2-13~P2-19는 B묶음(생존 B3 이후)이 사용한다. A묶음은 P2-20부터 쓴다. 수치는 모두 `data/tuning/noise_settings.tres`, `data/tuning/zombie_settings.tres`에 있다.

### 6.2 Phase 2-A에서 검증하지 못한 항목

- 성능 실측: 틱당 AI 시간, 좀비 수에 따른 서버 부하를 재지 않았다. 상한 64·틱당 8은 측정 없이 둔 값이다(CLAUDE.md §10).
- soak 범위: 좀비 20~24마리, 월드 3시간을 틱당 2 월드초로 가속한 단위 테스트뿐이다. 실제 틱 간격으로 여러 시간 서버를 돌려 보지 않았다.
- 네트워크: 좀비·소음은 복제되지 않는다. 두 클라이언트가 같은 좀비를 보는지는 N1/P2-Z에서 검증한다.
- 실제 서버 프로세스에서 좀비가 플레이어를 공격하는 흐름: 스모크 테스트는 12마리가 있는 서버가 뜨고 저장되는 것까지만 확인한다(좀비가 시야 밖에서 시작).
- 소음을 내는 실제 호출자(발소리, 전투)가 없어 "플레이어 행동 → 소음 → 좀비 반응"은 테스트에서 `emit`을 직접 부르는 형태로만 확인했다.
- 저장을 사이에 둔 틱 단위 재현(P2-31), 설정 상한보다 큰 좀비 수.

### 6.4 Phase 2-C에서 검증하지 못한 항목

- 네트워크: 전투 RPC가 없어 실제 클라이언트 요청 → 서버 판정 → 두 클라이언트가 같은 결과를 받는 흐름은 확인하지 못했다(N1, P2-Z). 요청 빈도 제한, 타입이 틀린 RPC 인자 검증도 N1 몫이다.
- 실제 서버 프로세스에서의 전투: 스모크 테스트는 전투 시스템이 등록된 서버가 뜨고 저장되는 것까지만 확인한다. 공격은 단위 테스트에서 `request_melee_attack`을 직접 불러 확인했다.
- 성능: 공격마다 모든 좀비와 모든 아이템(인벤토리 조회)을 훑는다. 좀비·아이템이 많을 때의 비용은 재지 않았다.
- 밸런스: 무기 수치는 플레이 테스트를 거치지 않았다.
- 좀비가 반격하는 실제 교전(좀비가 보고 물어뜯는 동안의 전투)은 전투 단위 테스트에서 격리했다(좀비 시야 0, 이동 속도 0). 좀비 쪽 반응은 좀비 테스트가 다룬다.

### 6.6 P2-A3에서 검증하지 못한 항목

- 실제 서버 프로세스: 클라이언트가 보낸 이동 의도 → 서버 이동 → 발소리 → 좀비 반응은 단위 테스트에서 `set_move_input`/`step_movement`/`step_systems`를 서버와 같은 순서로 직접 불러 확인했다. 실제 ENet 클라이언트로는 확인하지 않았다(스모크 테스트의 클라이언트는 움직이지 않는다).
- 성능: 걷는 플레이어가 많을 때 늘어나는 소음 수가 좀비 청각 조회 비용에 주는 영향, 소음 상한(256개)에서 오래된 소음이 밀려나는 상황은 재지 않았다.
- 월드 시간 배율이 1이 아닐 때: 발소리 간격은 이동 거리 기준이라 그대로지만 소음 수명은 월드 시간이라 살아 있는 소음 수가 달라진다. 배율 1에서만 테스트했다.
- 밸런스: 세기 8·보폭 2m는 플레이 테스트를 거치지 않았다. 기존 좀비·전투·네트워크 테스트는 발소리가 켜진 기본 설정에서 수정 없이 통과했지만, 그 테스트들이 발소리가 좀비 행동을 바꾸는 상황을 다루는지는 따로 확인하지 않았다.

## 7. P1-4 카메라/입력 임시 가정 (PROVISIONAL)

P1-4 프로토타입을 실행할 수 있게 하되 제품 정책으로 확정하지 않은 값이다. 모두 `data/tuning/camera_settings.tres`로 조정 가능하다.

| # | 항목 | 임시 가정(현재 구현) | 결정 필요 사항 |
|---|---|---|---|
| P1-4-1 | 마우스 감도 | 픽셀당 0.003 rad | 실제 플레이 테스트 후 기본 감도, X/Y 별도 설정, 반전 옵션 |
| P1-4-2 | 카메라 기하 | 거리 6m, 대상 높이 1.5m, 초기 피치 -0.35rad, 범위 -1.2~0.2rad | 새 캐릭터 모델/환경 충돌을 포함한 기본 구도와 줌 범위 |
| P1-4-3 | 키 바인딩 | 이동 W/S/A/D, 줍기 E(물리 키 기준) | 사용자 키 재설정 UI, 방향키/컨트롤러 기본 바인딩 |
| P1-4-4 | 입력/전송 튜닝 | 데드존 0.1, 유지 재전송 0.2초, 방향/yaw 변화 임계 0.01 | 입력 장치별 데드존과 네트워크 측정 후 재전송/변화 임계 조정 |
| P1-4-5 | 임시 플레이어 표현 | 반지름 0.4m·높이 1.8m 캡슐, 로컬 하늘색/원격 주황색 | 실제 모델/애니메이션 도입 시 크기·색 대체 |
