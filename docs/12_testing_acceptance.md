# 12. 테스트 및 수용 기준

## 1. 테스트 피라미드

1. 단위 테스트: 순수 계산/상태 전이/데이터 검증.
2. 통합 테스트: 서비스 간 흐름(인벤토리-제작, 건축-내비게이션 등).
3. 멀티플레이 테스트: 서버와 복수 클라이언트 동작.
4. 시나리오 테스트: NPC/쉘터/감염/사건 연쇄.
5. 성능 테스트: 활성 셀, NPC 수, 좀비 수, 네트워크 부하.
6. 장시간 테스트(soak): 저장, 메모리, AI 상태 정체, 서버 안정성.

### 1.1 규칙: 테스트 결과는 실제 시간·프레임 수에 기대지 않는다

부하가 큰 머신(Godot 여러 개가 동시에 도는 `tools/check.sh` 등)에서도 같은 결과가 나와야 한다. 결과가 실제로 흐른 시간이나 그 사이 지나간 프레임 수에 따라 달라지면 안 된다.

- 서버는 물리 틱(60 Hz)으로 진행한다. 결과를 정하는 기간(관찰 창, 휘두르는 간격, 걸은 거리, 쿨다운을 넘기는 시간)은 **서버 틱으로 센다**: `await tree.physics_frame`를 N번, `NetTestCluster.wait_ticks(n)`. `create_timer()`나 `Time.get_ticks_msec()`로 재지 않는다.
- 조건을 기다릴 때는 매 프레임 조건을 보고, 제한은 안전장치로만 둔다. 제한도 틱으로 센다: `NetTestCluster.wait_ticks_until(조건, 최대 틱)`. 시간이 다 되어 끝났다는 것 자체를 결과로 쓰지 않는다.
- `NetTestCluster`가 도는 동안 엔진은 프레임당 물리 틱을 최대 1번만 돌린다(`Engine.max_physics_steps_per_frame = 1`, `shutdown()`에서 되돌림). 기본값(8)이면 느린 프레임 하나를 서버 틱 여러 번으로 몰아서 따라잡고, 그 사이 네트워크 폴링이 없다. 그러면 클라이언트 미러가 틱 몇 개만큼 더 늦어지고, 미러를 보고 움직이는 테스트(좀비 앞에서 멈추기)가 더 멀리 간다. 2026-11-16 `phase2_acceptance_test`의 "물린 횟수 4 대 5"가 이것이었다. 밥이 좀비를 지나쳐 반대편에 섰고, 맞은 좀비가 밥 쪽으로 돌아서 앨리스가 시야 밖으로 나가 마지막 한 번은 밥을 물었다.
- 비신뢰 채널(좀비 스냅숏 등)로 **도착한** 개수는 부하에 따라 달라질 수 있다. 개수를 비교하는 단언은 서버가 **보낸** 개수로 한다(`ZombieNetModule.sent_snapshot_rows_to(peer_id)`). 받은 개수는 측정값으로 출력만 한다.
- 실제 시간을 써도 되는 곳: 서버나 클라이언트가 실제 시간으로 판정하는 것(요청 속도 제한, 클라이언트 연타 방지)을 맞추는 대기, 그리고 측정값(마이크로초)을 출력할 때.

## 2. 핵심 테스트 시나리오

### 2.1 생존
- 허기/갈증/피로가 시간/활동에 따라 변화.
- 부상에 따라 이동/작업/전투 성능 변화.
- 감염 진행과 치료 효과.

### 2.2 좀비
- 시야 내 플레이어 탐지.
- 소음 발생 후 조사.
- 시야 상실 후 마지막 위치 수색.
- 문/창/바리케이드 대응.
- 여러 좀비의 동일 소음 반응 최적화.

### 2.3 건축
- 자재 충분/부족.
- 유효/무효 위치.
- 동시 배치 요청.
- 파괴/수리.
- 방 인식 및 내비게이션 갱신.

### 2.4 NPC AI
- 욕구 충족 행동.
- 긴급 상황 인터럽트.
- 서로 다른 성격의 반응 비교.
- 비대칭 관계 저장.
- 기억 감쇠와 중요 기억 보존.
- 고정 seed 재현.
- 근거리/원거리 시뮬레이션 전환.

### 2.5 사회/사건
- 연애 상호 동의.
- NPC-NPC 관계 진행.
- 비밀 정보 공개 범위.
- 증거/목격 기반 조사.
- 범죄가 단일 감정값으로 발생하지 않음.

### 2.6 농업/가축
- 파종에서 수확까지.
- 계절/관수 영향.
- 생산/보관/부패.
- 가축 건강/먹이/생산.
- 좀비 공격/감염.

### 2.7 멀티플레이/저장
- 동시 루팅.
- 동시 건축.
- 연결 끊김 후 재접속.
- 서버 재시작 후 복구.
- 권한 없는 RPC 거절.
- 구역 스트리밍 후 상태 유지.

## 3. 성능 테스트 기준

초기에는 정량 목표를 임의로 확정하지 않는다. 테스트 장비/서버 사양을 먼저 명시하고 다음을 측정한다.
- 클라이언트 평균/1% low FPS.
- 서버 tick 시간과 최악 지연.
- 활성 NPC/좀비 수에 따른 AI 시간.
- 내비게이션 요청/갱신 시간.
- 네트워크 대역폭/지연/패킷 손실 시 동작.
- 저장/로드 시간과 파일 크기.
- 메모리 사용량 및 장시간 누수.

## 4. 버그 심각도

- P0: 저장 손실, 아이템 복제, 서버 권한 우회, 지속적인 크래시.
- P1: 주요 진행 차단, 치명적인 동기화 오류, 핵심 AI 정지.
- P2: 기능 일부 오작동/우회 가능.
- P3: 시각/사운드/경미한 UI 문제.

## 5. 완료 정의(Definition of Done)

- 요구사항이 구현되었다.
- 단위/통합/시나리오 테스트가 통과했다.
- 서버/클라이언트 역할이 검증되었다(해당 기능에 한함).
- 저장/복구 영향이 확인되었다.
- 로그/오류 처리가 있다.
- 문서가 구현과 일치한다.
- 미해결 이슈와 제한이 보고되었다.

## 6. 구현된 수용 테스트 (Phase 1~2, 2026-11-15)

수용 테스트는 `tests/scenarios/`에 있고 `tools/check.sh`가 매번 실행한다. 모두 서버 1 + 클라이언트 2를 한 프로세스 안에서 실제 ENet(localhost)으로 연결한다(`tests/framework/net_test_cluster.gd`). 여기 없는 §2 시나리오는 아직 수용 테스트가 없다(단위·통합 테스트만 있거나 미구현).

Phase 2 시나리오 파일은 `tests/scenarios/phase2_acceptance_test.gd`이다. 기본 조립을 격리하지 않고 쓰며(이동·줍기·공격 의도 RPC, 좀비 AI, 발소리, 생존 시간 규칙, NetModule 3개), 서버 쪽 직접 호출은 좀비 배치에만 쓴다. 조정한 설정값과 이유는 파일 머리 주석과 docs/15 §6.13에 있다.

| 수용 기준 | 테스트 | 증명하는 내용 |
|---|---|---|
| 상태 변화가 저장/복구 후 유지된다 | P2 교전(세션 2), P1 | 교전 뒤 서버를 내리고 저장에서 새 월드를 만든다. 플레이어 체력·상처·감염 단계와 경과 시간, 좀비 목록(죽은 좀비 없음, 남은 좀비의 위치·상태·체력), 전투 RNG, 월드 시각, 인벤토리가 저장 직전 값과 같고, 다시 접속한 두 클라이언트의 join 스냅샷이 그 값을 담고 있다. 복구된 상처는 계속 출혈한다 |

| 서버와 두 클라이언트가 전투 결과 및 감염 상태에 동의한다 | P2 교전, P2 감염 | 두 클라이언트가 같은 좀비를 죽일 때까지의 전투 이벤트 열이 서버 기록·A·B에서 전부 같다(제외 필드 없음). 감염은 docs/15 P2-9 해석대로 서버와 본인이 단계에 동의하고, 다른 클라이언트는 같은 물림 이벤트를 감염 결과·체력 없이 받는다 |
| 감염 단계 변화는 설정값으로 조정 가능하다 | P2 감염 | 잠복·초기 단계 시간을 두 가지 값으로 바꿔 각각 실행하면 서버의 단계 진입 시각이 설정값과 같고(오차 1e-6초), 본인 미러가 같은 시각의 이벤트로 따라간다 |
| 부상은 해당 신체 부위 관련 행동에 예측 가능한 페널티를 준다 | P2 다리, P2 팔 | 다리 물림: 같은 이동 의도를 보낸 두 플레이어의 틱당 서버 이동 거리 비가 `1 − 이동 페널티 × severity`. 팔 물림: 같은 무기의 피해가 `기본 피해 × (1 − 조작 페널티 × severity) × 굴림`. 배율은 본인 미러의 상처와 설정값으로 계산한다 |
