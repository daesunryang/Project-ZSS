# 12. 테스트 및 수용 기준

## 1. 테스트 피라미드

1. 단위 테스트: 순수 계산/상태 전이/데이터 검증.
2. 통합 테스트: 서비스 간 흐름(인벤토리-제작, 건축-내비게이션 등).
3. 멀티플레이 테스트: 서버와 복수 클라이언트 동작.
4. 시나리오 테스트: NPC/쉘터/감염/사건 연쇄.
5. 성능 테스트: 활성 셀, NPC 수, 좀비 수, 네트워크 부하.
6. 장시간 테스트(soak): 저장, 메모리, AI 상태 정체, 서버 안정성.

### 1.1 규칙: 테스트 결과는 실제 시간·프레임 수에 기대지 않는다

부하가 큰 머신(Godot 여러 개가 동시에 도는 `tools/check.sh` 등)에서도 같은 결과가 나와야 한다. 결과가 실제로 흐른 시간이나 그 사이 지나간 프레임 수에 따라 달라지면 안 된다.

- 서버는 물리 틱(60 Hz)으로 진행한다. 결과를 정하는 기간(관찰 창, 휘두르는 간격, 걸은 거리, 쿨다운을 넘기는 시간)은 **서버 틱으로 센다**: `await tree.physics_frame`를 N번, `NetTestCluster.wait_ticks(n)`. `create_timer()`나 `Time.get_ticks_msec()`로 재지 않는다.
- 조건을 기다릴 때는 매 프레임 조건을 보고, 제한은 안전장치로만 둔다. 제한도 틱으로 센다: `NetTestCluster.wait_ticks_until(조건, 최대 틱)`. 시간이 다 되어 끝났다는 것 자체를 결과로 쓰지 않는다.
- 이동 입력은 실제 시간 기준으로 오래되면 무효가 되므로, 이동 배율은 총거리 비율이 아니라 서버가 이동을 승인한 틱의 한 걸음 크기로 비교한다.
- `NetTestCluster`가 도는 동안 엔진은 프레임당 물리 틱을 최대 1번만 돌린다(`Engine.max_physics_steps_per_frame = 1`, `shutdown()`에서 되돌림). 기본값(8)이면 느린 프레임 하나를 서버 틱 여러 번으로 몰아서 따라잡고, 그 사이 네트워크 폴링이 없다. 그러면 클라이언트 미러가 틱 몇 개만큼 더 늦어지고, 미러를 보고 움직이는 테스트(좀비 앞에서 멈추기)가 더 멀리 간다. 2026-11-16 `phase2_acceptance_test`의 "물린 횟수 4 대 5"가 이것이었다. 밥이 좀비를 지나쳐 반대편에 섰고, 맞은 좀비가 밥 쪽으로 돌아서 앨리스가 시야 밖으로 나가 마지막 한 번은 밥을 물었다.
- 비신뢰 채널(좀비 스냅숏 등)로 **도착한** 개수는 부하에 따라 달라질 수 있다. 개수를 비교하는 단언은 서버가 **보낸** 개수로 한다(`ZombieNetModule.sent_snapshot_rows_to(peer_id)`). 받은 개수는 측정값으로 출력만 한다.
- 실제 시간을 써도 되는 곳: 서버나 클라이언트가 실제 시간으로 판정하는 것(요청 속도 제한, 클라이언트 연타 방지)을 맞추는 대기, 그리고 측정값(마이크로초)을 출력할 때.
- 측정 테스트의 실제 시간 상한은 `assert_true(ms < 상한)`이 아니라 `TestCase.assert_time_bound(ms, 상한, 설명)`으로 건다. 기본은 넘어도 경고 줄(`[timing] WARNING`)만 남기고, `ZSS_STRICT_TIMING=1`일 때만 실패한다. 같은 PC에서 다른 프로젝트의 Godot이 돌면 측정값이 몇 배로 뛰어 병합 검사가 막혔다(2026-11-17, 경로 탐색 측정 3.5 → 23 ms). 칸 수·계획 횟수처럼 결정적인 값은 그대로 `assert_true`로 단언한다.

## 2. 핵심 테스트 시나리오

### 2.1 생존
- 허기/갈증/피로가 시간/활동에 따라 변화.
- 부상에 따라 이동/작업/전투 성능 변화.
- 감염 진행과 치료 효과.

### 2.2 좀비
- 시야 내 플레이어 탐지.
- 소음 발생 후 조사.
- 시야 상실 후 마지막 위치 수색.
- 문/창/바리케이드 대응.
- 여러 좀비의 동일 소음 반응 최적화.

### 2.3 건축
- 자재 충분/부족.
- 유효/무효 위치.
- 동시 배치 요청.
- 파괴/수리.
- 방 인식 및 내비게이션 갱신.

### 2.4 NPC AI
- 욕구 충족 행동.
- 긴급 상황 인터럽트.
- 서로 다른 성격의 반응 비교.
- 비대칭 관계 저장.
- 기억 감쇠와 중요 기억 보존.
- 고정 seed 재현.
- 근거리/원거리 시뮬레이션 전환.

### 2.5 사회/사건
- 연애 상호 동의.
- NPC-NPC 관계 진행.
- 비밀 정보 공개 범위.
- 증거/목격 기반 조사.
- 범죄가 단일 감정값으로 발생하지 않음.

### 2.6 농업/가축
- 파종에서 수확까지.
- 계절/관수 영향.
- 생산/보관/부패.
- 가축 건강/먹이/생산.
- 좀비 공격/감염.

### 2.7 멀티플레이/저장
- 동시 루팅.
- 동시 건축.
- 연결 끊김 후 재접속.
- 서버 재시작 후 복구.
- 권한 없는 RPC 거절.
- 구역 스트리밍 후 상태 유지.

## 3. 성능 테스트 기준

초기에는 정량 목표를 임의로 확정하지 않는다. 테스트 장비/서버 사양을 먼저 명시하고 다음을 측정한다.
- 클라이언트 평균/1% low FPS.
- 서버 tick 시간과 최악 지연.
- 활성 NPC/좀비 수에 따른 AI 시간.
- 내비게이션 요청/갱신 시간.
- 네트워크 대역폭/지연/패킷 손실 시 동작.
- 저장/로드 시간과 파일 크기.
- 메모리 사용량 및 장시간 누수.

## 4. 버그 심각도

- P0: 저장 손실, 아이템 복제, 서버 권한 우회, 지속적인 크래시.
- P1: 주요 진행 차단, 치명적인 동기화 오류, 핵심 AI 정지.
- P2: 기능 일부 오작동/우회 가능.
- P3: 시각/사운드/경미한 UI 문제.

## 5. 완료 정의(Definition of Done)

- 요구사항이 구현되었다.
- 단위/통합/시나리오 테스트가 통과했다.
- 서버/클라이언트 역할이 검증되었다(해당 기능에 한함).
- 저장/복구 영향이 확인되었다.
- 로그/오류 처리가 있다.
- 문서가 구현과 일치한다.
- 미해결 이슈와 제한이 보고되었다.

## 6. 구현된 수용 테스트 (Phase 1~2, 2026-11-15)

수용 테스트는 `tests/scenarios/`에 있고 `tools/check.sh`가 매번 실행한다. 모두 서버 1 + 클라이언트 2를 한 프로세스 안에서 실제 ENet(localhost)으로 연결한다(`tests/framework/net_test_cluster.gd`). 여기 없는 §2 시나리오는 아직 수용 테스트가 없다(단위·통합 테스트만 있거나 미구현).

## 8. 실제 프로세스 강제 종료·복구 점검

`tools/crash_recovery_check.sh`는 별도 headless 전용 서버와 클라이언트를 실행해 정상 종료 후 재시작, 시작 직후 강제 종료, 두 클라이언트 접속 중 강제 종료, 저장 `.tmp` 파일이 실제로 나타난 동안의 강제 종료를 점검한다. 재시작 로그의 로드 세대·플레이어 수와 디스크 manifest를 맞춰 보고, manifest 중복·누락·깨진 JSON, manifest가 `.tmp`를 사용하지 않는지, 무시된 orphan `.tmp`, 테스트 맵의 중복 시드 여부도 검사한다. 기본값은 네 시나리오를 5회 반복하며 하나라도 실패하면 0이 아닌 코드로 끝난다.

Godot 4.7.2 실행 파일을 지정해 Git Bash에서 실행한다.

```bash
GODOT=/path/to/Godot_v4.7.2-stable tools/crash_recovery_check.sh
```

반복 수는 빠른 도구 자체 점검에만 `CRASH_ROUNDS=1`처럼 바꿀 수 있다. 실패한 실행의 로그와 저장 파일은 출력된 임시 경로에 남고, 성공 실행도 보존하려면 `CRASH_KEEP_WORK=1`을 쓴다.

### 9.2 바뀐 파일에 맞는 테스트만 돌리기

```bash
tools/test_changed.sh [<기준 커밋>] [--dry-run] [--list] [--no-smoke]
```

- 바뀐 파일: `git diff --name-only <기준>`(기준 뒤에 커밋한 것, 스테이징한 것, 안 한 것)과 추적하지 않는 새 파일. 기준을 안 주면 이 브랜치가 `main`에서 갈라진 커밋이고, 그렇게 해서 바뀐 것이 없으면(`main` 위, 깨끗한 작업 트리) 직전 커밋(`HEAD~1`)이다.
- 무엇을 돌릴지는 `tests/test_changes.cfg`가 정한다. 한 줄이 `<경로 패턴(확장 정규식)> <대상>...`이고, 바뀐 경로에 맞는 줄은 전부 적용한다.

| 바뀐 것 | 돌리는 것 |
|---|---|
| 문서만 (`docs/`, `notes/`, `*.md`) | 없음 |
| 코드가 하나라도 있음 | P0 단계 전체 + 지도가 가리키는 테스트 + 스모크 테스트 |
| 지도에 없는 경로 | P0 단계 + 스모크 |
| 전투·좀비·생존·내비게이션·자세 (도메인 코드, 그 네트워크 모듈과 미러, 조정값, 무기 정의), 소음, 이동 규칙, `tests/bot/` | 위에 더해 그 영역의 테스트와 **전투 봇** |
| 저장 (`scripts/services/save/`, 월드 셀) | 위에 더해 저장·지속성 테스트 |
| 건축·보관함·인벤토리·거래·맵·캐릭터·표시 | 위에 더해 그 영역의 테스트 |

| 성능 벤치 (`tools/perf_bench*`, `tools/perf_client.gd`) | 위에 더해 `perf_bench_digest_test` |
| 바뀐 테스트 파일 | 그 파일 자신 |
| `scripts/core/`, `server_world.gd`, `tests/framework/`, `tests/run_tests.gd`, `project.godot` | 전부 |
| 네트워크 뼈대(`network_service.gd`, `net_module.gd` 등) | P0 + 통합·시나리오 테스트 전부 |

- 바뀐 경로마다 어느 줄이 무엇을 골랐는지, 그리고 실제로 실행할 명령을 출력한다. `--dry-run`은 거기서 멈추고, `--list`는 고른 테스트 파일 목록까지 보여 준다.
- 지도의 대상은 테스트 파일 경로에 들어 있는 글자다(`combat_` → `combat_rules_test.gd`, `combat_service_test.gd`, `combat_net_test.gd`). 특별한 대상은 `none`, `p0`, `all`, `bot`, `self` 다섯 개다.
- `tools/test_changed_selftest.sh`가 알려진 경로에 대한 선택 결과를 Godot 없이 확인한다(문서만 → 없음, 모르는 경로 → P0, 전투·좀비·생존·내비게이션·자세 → 봇 포함 등 24가지). `test_tiers_test.gd`는 지도의 모든 대상이 실제 테스트 파일을 가리키는지 확인한다.
- 병합 전 전체 검사는 그대로 `tools/check.sh`다(선택 자체 점검 → 전체 테스트(봇 포함) → 스모크).

### 9.3 전투 봇

플레이어 조작만 쓰는 봇이 화면 없이 좀비 전투 장면을 하나씩 싸우고, 장면마다 깼는지, 걸린 모의 시간, 잃은 체력, 때린 횟수와 맞은 횟수를 남긴다.

```bash
tools/combat_bot.sh                      # 모든 장면
tools/combat_bot.sh one_zombie_open      # 한 장면 (scene_id, 쉼표로 여러 개)
ZSS_BOT_TRACE=30 tools/combat_bot.sh ... # 휘두름·피격마다 한 줄, 30틱마다 상태 한 줄
```

- **봇이 쓰는 것**: 서버 1 + 클라이언트 1을 한 프로세스에서 실제 ENet으로 잇고(`NetTestCluster`, 운영 조립), 봇은 그 클라이언트다. 자기 클라이언트 미러(위치, 좀비, 자기 체력·스태미나·상처, 자세, 인벤토리, 바닥 아이템, 구조물)만 보고, 클라이언트 요청 함수만 부른다: 이동+방향, 근접 공격, 자세, 줍기, 아이템 사용(붕대), 문 열기. 좀비를 다치게 하거나 자기를 옮기는 서버 API는 쓰지 않는다.
- **하네스가 서버에서 하는 것**: 싸움 전 준비(장면의 아이템을 월드 시드로 깔기, 좀비를 `spawn_zombie`로 놓기), 정해진 시각에 시작하려고 서버 시계 읽기, 싸움 뒤 살아 있는 좀비 수 확인. 그 밖에는 없다.
- **정책**(`tests/bot/combat_bot_policy.gd`, 순수 규칙): 엎드려 있으면 일어난다 → 손 닿는 무기·붕대를 줍고 출혈이 있으면 붕대를 쓴다 → 가장 가까운 좀비가 목표 → 휘두를 수 있으면 사거리 안에 들어온 목표를 친다(다가오는 좀비는 기다리고, 안 오는 좀비에게는 걸어가고, 길 위의 닫힌 문은 연다) → 휘두를 수 없으면(쿨다운, 스태미나) 모든 좀비에게서 2.1 m 넘게 떨어진다. 잘 싸우는 봇이 아니라 같은 자로 다시 재기 위한 봇이다.
- **장면은 데이터다**: `tests/bot/scenes/*.tres`(`CombatBotScene`). 시드, 시작 위치, 엎드린 채 시작 여부, 테스트 맵 사용 여부, 좀비 위치·방향, 바닥 아이템, 모의 시간 한도, 깨야 하는지(`expect_cleared`), 두 번 돌려 비교할지(`verify_repeat`). 파일을 더하면 장면이 늘어난다.
- **실패 조건**: 깨야 하는 장면을 한도 안에 못 깼다, 같은 시드 두 번의 결과가 다르다, 실행을 준비하지 못했다. 걸린 시간과 잃은 체력은 기록만 한다.
- **기록**: 표를 출력하고, 장면마다 한 줄을 `user://combat_bot/results.log`에 덧붙인다(날짜, 커밋, 장면, 시드, 결과, 모의 시간, 잃은 체력, 때린·맞은 횟수, 휘두른 횟수, 잡은 수, 무기, 반복 비교, 실제 시간). `ZSS_BOT_LOG`로 위치를 바꾼다.
- **전투 코드를 고치면 같이 돈다**: `tools/test_changed.sh`가 §9.2 표의 경로에서 봇을 고른다. `tools/check.sh`는 언제나 돌린다.

같은 시드가 같은 결과를 내도록 하네스(`tests/bot/combat_bot_runner.gd`)가 하는 일:

1. 봇은 서버 60번째 틱에 참가를 요청하고 싸움은 행동 시각 2.0초에 시작한다(접속에 걸리는 시간이 결과에 섞이지 않게).
2. 매 틱, 봇이 보기 전과 행동한 뒤에 테스트 전용 NetModule(`CombatBotSyncModule`)의 표식을 서버까지 왕복시키며 양쪽 소켓을 직접 폴링한다. 답이 돌아오면 그 전에 보낸 것은 다 도착했다. 봇은 언제나 "직전 틱까지의 상태"를 보고, 봇의 요청은 언제나 다음 서버 틱 전에 도착한다.
3. 서버가 실제 시간으로 재는 규칙(요청 속도 제한, 이동 입력 만료)은 걸리지 않을 값으로 둔다.
4. ENet이 비신뢰 패킷을 버리지 않게 한다: 서버 호스트의 대역폭 제한을 풀고(docs/15 TT-001), 양쪽 스로틀이 내려가지 않게 하고, 스로틀이 가득 열려 있지 않으면 그 실행을 오류로 끝낸다.
5. 모의 시간은 틱으로 센다. 실행은 4배속이지만 틱 하나는 1/60초 그대로다.
