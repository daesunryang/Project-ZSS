# 08. 멀티플레이 및 서버 네트워크 명세

## 1. 목표

여러 플레이어가 동일한 지속 월드에서 생존/건축/탐험/사회 시스템을 공유한다. 서버가 월드의 최종 상태를 관리한다.

## 2. 초기 네트워크 범위

- 협동 PvE 우선.
- 초기 검증 목표 1~4명 동시 플레이(확정된 제품 상한이 아님).
- PvP/플레이어 절도/플레이어 간 살해는 기본 비활성화.
- Dedicated headless server 지원을 목표로 한다.
- 서버와 클라이언트는 동일한 Godot 프로젝트/프로토콜 기반을 사용한다.

## 3. 권한 모델

### 서버 권한으로 처리할 것

- 플레이어의 최종 위치/이동 검증.
- 아이템 획득/소비/거래/제작.
- 공격/피해/사망/감염.
- 좀비/NPC AI 및 월드 이벤트.
- 건축 배치/철거/내구도/공사 진행.
- 작물 성장, 식품 부패, 가축 상태.
- 관계/기억/범죄/사건.
- 월드 시간/날씨/저장.

### 클라이언트가 담당할 것

- 입력 수집.
- 카메라/애니메이션/오디오/시각 효과.
- UI 표시.
- 예측 가능한 이동의 시각적 보간/초기 client prediction.
- 상호작용 의도 요청.

## 4. 통신 패턴

`Client Intent → Server Validation → Authoritative State Change → Replication → Client Presentation`.

클라이언트 요청은 명령 이름, 대상 ID, 필요한 입력만 전달한다. 서버는 요청을 검증하고 성공/실패 결과 및 변경된 상태를 반환한다.

## 5. RPC 보안

모든 RPC에서 확인:
- 발신 peer 식별.
- 타입/길이/값 범위.
- 대상 엔티티 존재 및 권한.
- 거리/시야/상호작용 가능 상태.
- 인벤토리/자원/쿨다운.
- 요청 빈도 제한.
- 게임 상태 전이 유효성.

클라이언트가 최종 좌표/피해량/아이템 수량/월드 시간/AI 결과를 보낼 수 없게 한다.

## 6. 엔티티 복제

- 플레이어/NPC/좀비 등 네트워크 엔티티에는 안정된 network entity ID가 필요하다.
- `MultiplayerSpawner`는 서버 권한 스폰 복제에 사용할 수 있다.
- `MultiplayerSynchronizer`는 적절한 상태 동기화에 사용할 수 있으나, 무엇을 어떤 주기로 복제할지 명시한다.
- 대량 정적 데이터 전체를 반복 전송하지 않고 ID와 변경 델타 중심으로 전송한다.
- 연결/재접속 시 초기 스냅샷과 이후 델타의 순서를 보장한다.

## 7. 메시지 분류

| 메시지 | 신뢰성 권장 | 설명 |
|---|---|---|
| 인벤토리/거래/건축 커밋 | reliable | 상태 손실 금지 |
| 관계/사건/저장 알림 | reliable | 이벤트 결과 보장 |
| 이동 입력/상태 | 측정 후 선택 | 낮은 지연과 순서 중요 |
| 위치 스냅샷 | unreliable ordered 후보 | 최신 상태 우선 |
| 사운드/시각 효과 | unreliable 가능 | 유실 허용 여부 검토 |

정확한 channel과 transfer mode는 프로토타입에서 네트워크 프로파일링 후 결정한다.

## 8. 동시성 및 트랜잭션

- 아이템 이동/거래/제작은 하나의 서버 트랜잭션으로 처리한다.
- 두 플레이어가 같은 루팅 아이템을 동시에 획득하면 서버가 먼저 승인한 요청만 성공한다.
- 건축 배치/철거도 서버의 순차 검증으로 충돌을 방지한다.
- 자원 소모와 결과 생성은 부분 성공 상태가 남지 않도록 원자적으로 처리한다.

## 9. 접속/종료/재접속

- 플레이어 연결 시 인증/서버 정책 검증 후 플레이어 상태를 불러온다.
- 갑작스러운 연결 종료 시 캐릭터 상태를 안전하게 저장한다.
- 기본 협동 서버는 플레이어가 모두 나가면 월드 시간을 정지하는 방식을 제안한다.
- 지속 서버는 별도 설정으로 오프라인 진행을 켠다.
- 재접속 시 위치/인벤토리/건강/관계/소유권이 복구된다.

## 10. 호스트 이동

초기 설계는 전용 서버 기준이다. listen-server/host migration은 MVP에서 제외한다. 필요해지면 별도 ADR을 작성한다.

## 11. 서버 장애

- 주기 저장 또는 이벤트 기반 저장.
- 원자적 저장 파일 교체.
- 마지막 정상 저장부터 복구.
- 손상된 청크는 격리하고 다른 데이터 복구를 시도한다.
- 서버 로그는 월드 ID, 플레이어 ID, 엔티티 ID, 요청 ID를 포함한다.

## 12. 수용 기준

- 2개 클라이언트에서 같은 아이템/건축/좀비/감염 상태가 관찰된다.
- 조작된 RPC 입력이 거절된다.
- 동시 루팅/거래 요청으로 복제/소실이 없다.
- 접속 종료 후 다시 접속하면 플레이어 상태가 복구된다.
- 서버 재시작 후 세계 상태가 복구된다.

## 13. 관심 영역 관리 (P3-2 구현 현황, 임시)

§6의 "대량 정적 데이터 전체를 반복 전송하지 않는다"를 셀 단위로 구현한 것이다. 계약은 docs/09 §15.2, 임시 수치와 측정값은 docs/15 §15.2.

- **범위의 기준은 서버 위치다.** 접속자마다 자기 플레이어가 있는 셀에서 2칸 이내(50m 셀에서 100~150m)의 셀이 "관심 셀"이고, 한번 관심 셀이 된 셀은 3칸보다 멀어져야 빠진다(경계를 왔다 갔다 해도 깜빡이지 않는다). 클라이언트가 보낸 위치·요청은 범위 계산에 쓰이지 않는다.
- **관심 셀의 것만 받는다.** 월드에 놓인 아이템과 좀비(위치 스냅샷, 이벤트)는 그 셀에 관심 있는 접속자에게만 간다. 접속할 때의 초기 스냅샷도 같은 범위로 잘린다. 셀을 얻으면 그 셀의 내용이 오고, 잃으면 미러에서 빠진다. 서버 메모리에 없는 셀은 누구에게도 가지 않는다.
- **초기 스냅샷과 이후 델타의 순서**(§6): 접속 스냅샷이 그 접속자의 첫 관심 셀을 정하고, 그 뒤의 얻음·잃음·변화는 같은 reliable 채널로 뒤따른다. 좀비 이벤트는 접속자마다 자기 순번(1부터, 구멍 없음)으로 간다.
- **플레이어는 아직 전역이다.** 다른 플레이어의 위치·생사·자세·이름은 거리와 무관하게 모든 접속자에게 간다(임시, docs/15 P3-041).
- **자기 행동의 결과는 항상 온다.** 요청의 결과(줍기·내려놓기·공격)와 본인 소지품·본인 상태는 범위와 무관하게 요청자·소유자에게 간다. 반대로 범위 밖 엔티티에 관한 것은 거부 사유로도 드러나지 않는다(§5, docs/00 ADR-009): 받은 적 없는 아이템 ID에 대한 줍기 요청은 "없는 ID"와 같은 사유로 거부된다. 판정 자체는 계속 서버의 사거리 검사뿐이다.
- §12의 "2개 클라이언트에서 같은 아이템/좀비 상태가 관찰된다"는 **같은 관심 셀을 보는 클라이언트 사이**의 기준이다. 걸어온 길이 다르면 바깥 한 줄(유지 고리)이 다를 수 있다.

## 14. ENet 전송 압축 (PERF-2)

- `NetworkSettings.compression_mode`가 ENet 호스트 압축을 정한다. 서버와 모든 클라이언트는 `create_server`/`create_client` 성공 직후 `ENetMultiplayerPeer.host.compress(mode)`를 적용한다.
- 이 값은 `BuildInfo.PROTOCOL_VERSION`과 함께 서버·클라이언트가 반드시 공유할 접속 계약이다. 서로 다르면 ENet 연결 자체가 성립하지 않아 join 거부 RPC를 받을 수 없다. 클라이언트는 연결 시작 로그에 자기 압축 모드와 "서버와 같아야 한다"는 안내를 남겨, 뒤의 일반 연결 실패 로그와 함께 원인을 찾게 한다.
- 기본값은 PERF-2 측정에서 종합 비용이 가장 좋았던 `COMPRESS_FASTLZ`다. `NONE`, `RANGE_CODER`, `FASTLZ`, `ZLIB`, `ZSTD`만 설정 검증을 통과한다. ZSTD는 4KB보다 작은 패킷이 대부분인 현재 트래픽의 기본값으로 쓰지 않는다.
- 압축은 페이로드를 바꾸지 않으므로 프로토콜 버전 15는 올리지 않았다. 배포·접속 설정에서는 프로토콜 버전과 압축 모드를 한 묶음으로 맞춘다.

### 14.1 ENet 호스트 인자와 대역폭 (2026-11-19)

- 서버: `create_server(port, max_players + TRANSPORT_HEADROOM, CHANNEL_COUNT)`. 클라이언트: `create_client(address, port, CHANNEL_COUNT)`. Godot 4.7 문서의 순서는 `create_server(port, max_clients, max_channels, in_bandwidth, out_bandwidth)`, `create_client(address, port, channel_count, in_bandwidth, out_bandwidth, local_port)`이고 대역폭 0은 무제한이다.
- 두 호스트 모두 만든 직후, 압축을 걸기 전에 `host.bandwidth_limit(NetworkSettings.UNLIMITED_BANDWIDTH, UNLIMITED_BANDWIDTH)`(0, 0)을 부른다. 서버는 아직 아무도 접속하기 전이다.
- 이유: Godot 4.7.2에서 `create_server`에 `max_channels > 0`을 주면 대역폭 인자를 0으로 줘도 서버 호스트에 아주 작은 수신 대역폭 제한이 남는다. 접속하는 클라이언트는 그 제한을 전달받고, 클라이언트의 ENet이 비신뢰 패킷(이동 의도)을 보내기 전에 버린다(측정과 경과는 docs/15 TT-001). `create_server` 뒤의 `bandwidth_limit(0, 0)`은 지우면 안 된다. `tests/integration/enet_bandwidth_net_test.gd`가 지킨다.
- 대역폭 제한을 실제로 쓰고 싶어지면 이 호출의 값을 설정으로 빼고, 제한이 비신뢰 패킷을 버린다는 점을 같이 잰다.
