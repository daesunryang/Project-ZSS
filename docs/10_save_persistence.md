# 10. 저장·복구·데이터 버전 관리 명세

## 1. 원칙

- 월드 상태의 단일 권한은 서버다.
- 영속 엔티티는 안정적인 UUID/ID를 가진다.
- 저장 데이터는 스키마 버전을 가진다.
- 저장은 원자적으로 수행하고, 장애 시 마지막 정상 저장으로 복구한다.
- Node 경로/RID/메모리 주소를 저장하지 않는다.

## 2. 저장 대상

- 월드 설정/시간/날씨/난수 상태.
- 플레이어 위치/건강/인벤토리/장비.
- NPC 정체성/건강/욕구/감정/기억/관계/목표/업무.
- 좀비 상태 및 중요 군집 정보.
- 건축물/가구/쉘터/권한.
- 아이템 월드 인스턴스 및 루팅 상태.
- 밭/작물/가축.
- 외부 세력/관계.
- 사건 원장/증거/소문.

## 3. 저장 디렉터리 제안

```text
user://saves/<world_id>/
  manifest.json
  world_state.json
  players/<player_id>.json
  cells/<cell_id>.json
  npcs/<npc_id>.json
  shelters/<shelter_id>.json
  events/<event_partition>.json
  backups/<timestamp>/...
```

저장 파일이 많아질 경우 청크/엔티티 그룹화 및 압축 방식을 조정한다. 초기 버전은 JSON 기반으로 읽기 쉬운 저장을 우선한다. 성능/파일 수/손상 복구를 검증한 후 SQLite 또는 다른 저장소 도입을 별도 결정한다.

## 4. 저장 절차

1. 서버가 저장 시점의 상태 스냅샷을 만든다.
2. 새 데이터는 임시 파일에 기록한다.
3. 기록 후 parse/validation을 수행한다.
4. 정상 확인 시 기존 파일을 백업하고 임시 파일을 원본으로 교체한다.
5. manifest에 generation/version/time을 업데이트한다.
6. 실패 시 원본을 유지하고 오류를 기록한다.

## 5. 저장 스케줄

- 주요 트랜잭션은 즉시 또는 이벤트 큐에 커밋한다.
- 월드 스냅샷은 설정된 간격으로 저장한다.
- 서버 종료 신호 시 정상 저장을 시도한다.
- 구역 unload 전 해당 구역을 저장한다.
- 저장 주기는 성능과 데이터 손실 허용 범위를 테스트해 결정한다.

## 6. 스키마 버전/마이그레이션

각 저장 파일에 `schema_version`을 포함한다. 버전 N → N+1 마이그레이션 함수를 제공한다. 마이그레이션 전 백업을 생성하고, 부분 마이그레이션 실패 시 원본을 보존한다.

## 7. 무결성

- 중복 ID 검사.
- 참조 대상이 없는 관계/소유권 검사.
- 아이템 중복 소유 검사.
- 파괴된 건물/삭제된 NPC 참조 검사.
- 월드 시간 역행 검사.
- 저장 이후 이벤트 중복 처리 방지용 event sequence 관리.

## 8. 수용 기준

- 저장 → 프로세스 종료 → 다시 시작 → 로딩 후 핵심 상태가 동일하다.
- 손상된 파일이 있어도 가능한 다른 영역의 데이터 복구를 시도한다.
- 구버전 저장 데이터의 마이그레이션 테스트가 있다.
- 저장 중 서버가 종료되어도 마지막 정상 세이브를 잃지 않도록 한다.
