# 테스트 단계(P0/P1)·변경 기반 선택·전투 봇 — 작업 중 정한 것

브랜치 `test-tiers`, 2026-11-19. 구현 설명과 기준 결과는 `docs/12_testing_acceptance.md` §9, 남은 문제는 `docs/15_risks_and_open_questions.md` §16.6에 있다. 이 파일은 작업하면서 새로 정한 것과 그 이유만 적는다.

## 1. 사용자 지시 (원문 그대로)

> [3 자동 테스트] 테스트를 "깨지면 게임이 안 되는 것(P0)"과 "게임 전반(P1)"으로 나누고, 바뀐 파일에 맞는 단계만 골라 돌리는 명령을 만들어 줘. 보스마다 플레이어 조작만 쓰는 봇이 화면 없이 싸워서 깼는지, 걸린 시간, 잃은 체력을 남기게 하고, 전투 코드를 고치면 같이 돌게 해.

총괄(코디네이터)이 덧붙인 해석: LAST HAVEN에는 아직 보스가 없으므로 "보스마다"를 "좀비 전투 장면마다"로 적용하고, 나중에 보스 장면을 더하는 일은 데이터만 바꾸면 되게 한다.

## 2. 2026-11-19에 정한 것

### 2.1 단계 나누기

- P0는 사용자 말 그대로 "깨지면 게임이 안 되는 것"이다. 구체적으로는 게임이 뜬다(스크립트 컴파일, 부트스트랩, 실행 인자, 빌드 정보), 접속·참가·이동이 된다, 저장하고 되살린다, 위조·조작 요청을 거절한다, 핵심 거래가 맞다(인벤토리 보존, ID), Phase 1·2·3 수용 시나리오가 통과한다. 여기에 단계 목록과 변경 지도 자체를 지키는 `test_tiers_test.gd`를 넣었다.
- P1은 나머지 전부다("게임 전반").
- 한 파일에 P0 성격과 P1 성격의 테스트가 섞여 있어도 파일 단위로만 나눈다. 테스트 함수 단위로 나누면 목록이 1,000줄을 넘고, 새 테스트를 넣을 때마다 목록을 고쳐야 한다.
- 위조 요청 거절은 거의 모든 `*_net_test.gd`에 조금씩 들어 있다. P0에는 전투(`combat_net_test`)와 인벤토리(`inventory_net_test`), 그리고 수용 시나리오(P2·P3가 조작 요청을 직접 보낸다)만 넣었다. 나머지는 P1이다. 전부 넣으면 P0가 "몇 분"을 넘는다.
- 새 테스트 파일은 `tests/test_tiers.cfg`에 한 줄을 넣지 않으면 `test_tiers_test.gd`가 실패한다. 기본은 p1이고, 위 P0 항목을 지키는 파일만 p0로 넣는다.
- 전투 봇(`combat_bot_test.gd`)은 P1이다. P0에 넣으면 P0가 2분 넘게 길어진다. 대신 전투 관련 파일이 바뀌면 선택 명령이 봇을 같이 돌리고, `tools/check.sh`(전체 검사)는 언제나 돌린다.

### 2.2 선택 명령 `tools/test_changed.sh`

- 기준 커밋을 안 주면 이 브랜치가 `main`에서 갈라진 커밋(`git merge-base HEAD main`)과 비교한다. 커밋한 것, 스테이징한 것, 안 한 것, 추적 안 하는 새 파일을 모두 본다. 그렇게 봤을 때 바뀐 것이 하나도 없으면(`main` 위에 있고 작업 트리가 깨끗할 때) 직전 커밋(`HEAD~1`)과 비교한다. 이유: 에이전트는 worktree 브랜치에서 일하므로 "이 브랜치가 바꾼 것 전부"가 맞고, 총괄은 병합 직후 `main`에서 돌리므로 "방금 들어온 커밋"이 맞다.
- 문서만 바뀌면(`docs/`, `notes/`, `*.md`, `.gitignore`, `*.uid`) 아무것도 돌리지 않는다.
- 코드가 하나라도 바뀌면 P0 단계 전체와 스모크 테스트(실제 프로세스로 서버 1 + 클라이언트 2 접속)를 돌린다. 스모크는 P0의 "뜬다, 접속한다, 참가한다"를 실제 프로세스로 보는 유일한 검사라서 P0 수준 검사로 쳤다. `--no-smoke`로 뺄 수 있다.
- 지도(`tests/test_changes.cfg`)에 없는 경로는 P0만 돌린다.
- 모든 것이 기대는 파일(`scripts/core/`, `server_world.gd`, `tests/framework/`, `tests/run_tests.gd`, `project.godot`)이 바뀌면 전부 돌린다. `network_service.gd` 같은 네트워크 뼈대는 통합·시나리오 테스트 전부를 돌린다.
- 지도의 대상은 "테스트 파일 경로에 들어 있는 글자"로 적는다(`combat_` → `combat_rules_test.gd`, `combat_service_test.gd`, `combat_net_test.gd`). 소스 파일과 테스트 파일을 하나씩 짝짓지 않은 이유: 새 테스트가 이름 규칙만 따르면 지도를 안 고쳐도 잡힌다.
- 선택 결과가 맞는지는 Godot 없이 도는 `tools/test_changed_selftest.sh`가 확인하고, `tools/check.sh`가 맨 먼저 돌린다.

### 2.3 전투 봇

- 봇이 쓰는 것은 플레이어 클라이언트가 보내는 요청뿐이다: 이동+방향, 근접 공격, 자세, 줍기, 아이템 사용(붕대), 문 열기. 보는 것은 자기 클라이언트 미러뿐이다.
- 하네스가 서버에서 하는 일은 세 가지로 한정했다. (1) 싸움 전 준비: 장면의 아이템을 월드 시드로 깔고 좀비를 `spawn_zombie`로 놓는다(기존 시나리오 테스트와 같은 방식). (2) 시작 시각을 맞추려고 서버 시계(`action_time_sec`)를 읽는다. (3) 싸움이 끝난 뒤 살아 있는 좀비 수를 세어 클라이언트가 본 것과 맞는지 확인한다.
- 정책은 "치고 빠지기" 하나다. 휘두를 수 있으면 사거리 안에 들어온 가장 가까운 좀비를 치고, 못 휘두르는 동안(쿨다운, 스태미나 부족)은 좀비 손이 닿는 거리(1.5 m) 밖으로 물러난다. 잘 싸우는 봇이 목적이 아니라 전투 코드가 바뀌었을 때 같은 자로 다시 재는 것이 목적이다.
- 장면은 `tests/bot/scenes/*.tres` 파일이다. 파일을 하나 더하면 장면이 하나 늘어난다. 보스가 생기면 `CombatBotScene`에 "무엇을 놓을지" 칸을 하나 더하는 일은 필요하지만, 장면을 고르고 돌리고 기록하는 코드는 그대로다.
- "깨야 하는 장면"(`expect_cleared`)이 제한 시간(모의 시간) 안에 안 깨지거나 같은 시드 두 번의 결과가 다르면 실패한다. 걸린 시간과 잃은 체력은 기록만 한다(조정값을 바꿀 때마다 움직이므로).
- 결과 줄은 `user://combat_bot/results.log`에 덧붙인다(Windows: `%APPDATA%/Godot/app_userdata/LAST HAVEN/combat_bot/results.log`). 저장소 안에 두면 돌릴 때마다 작업 트리가 더러워진다. `ZSS_BOT_LOG`로 바꿀 수 있다.

### 2.4 같은 시드 → 같은 결과를 만들려고 넣은 것

처음에는 같은 장면을 두 번 돌리면 결과가 달랐다. 원인을 하나씩 찾아 없앴다.

1. 접속에 걸리는 시간이 실행마다 달라서 서버가 시작부터 세는 것(스냅숏 주기)과 첫 플레이어부터 세는 것(행동 시계)의 위상이 달랐다. → 봇은 서버 60번째 틱에 참가를 요청하고, 싸움은 행동 시각 2.0초에 시작한다.
2. 패킷이 어느 프레임에 도착하는지가 머신 속도에 달려 있었다. → 매 틱 봇이 보기 전과 행동한 뒤에, 테스트 전용 NetModule(`CombatBotSyncModule`)의 표식을 서버까지 왕복시키며 양쪽 소켓을 직접 폴링한다. 표식의 답이 돌아오면 그 전에 보낸 것은 전부 도착한 것이다.
3. 요청 속도 제한과 "이동 입력이 오래됨" 판정은 서버가 실제 시간으로 잰다. → 봇 실행에서는 걸리지 않을 만큼 넉넉한 값으로 둔다(제한 자체는 `*_net_test.gd`가 검사한다).
4. ENet이 비신뢰 패킷(이동 의도, 위치·좀비 스냅숏)을 버릴 수 있다. → 양쪽 스로틀이 내려가지 않게 하고, 스로틀이 가득 열려 있지 않으면 그 실행을 오류로 끝낸다.
5. 4번을 찾다가 Godot 문제를 발견했다(아래 2.5).

### 2.5 발견: 서버 ENet 호스트에 초당 5바이트 수신 제한이 걸린다 (게임 코드는 고치지 않았다)

- Godot 4.7.2의 `ENetMultiplayerPeer.create_server(port, max_clients, max_channels)`는 `max_channels > 0`이면 호스트의 **수신 대역폭 제한**을 `max_channels + 2` 바이트/초로 만든다(인자 자리가 한 칸 밀린 것으로 보인다). 게임은 채널 3개를 쓰므로 5바이트/초가 된다.
- 측정(2026-11-19, 봇 문 장면, 4배속): 싸움 시작부터 104틱까지 클라이언트 쪽 ENet 스로틀과 그 한도(`PEER_PACKET_THROTTLE`, `PEER_PACKET_THROTTLE_LIMIT`)가 32 만점에 1이었고 108틱 무렵 한도가 32로 돌아왔다. 그 108틱 동안 클라이언트는 이동 의도를 틱마다 하나씩(순번 1~109) 보냈는데, 4틱마다 본 서버의 "마지막으로 받은 순번"은 여섯 번만 바뀌었다(23, 32, 55, 64, 87, 96). 서버가 거절한 요청은 0건이다(도착하지 않았으므로 셀 것이 없다). 서버 호스트에 `bandwidth_limit(0, 0)`을 부르자 스로틀이 32에 머물고 서버의 순번이 클라이언트 순번을 그대로 따라왔다.
- 실제 게임에 주는 영향(추정, 실제 창에서 재지 않았다): 클라이언트가 보내는 이동 입력의 대부분이 한동안 서버에 가지 않는 구간이 되풀이될 수 있다(ENet은 이 한도를 1초마다 다시 계산한다). 서버는 마지막 입력을 0.5초 동안 계속 쓰므로 방향 전환·정지가 늦게 먹을 수 있다.
- 이 브랜치에서는 `scripts/`를 고치지 않았다. 범위가 테스트 도구이고, 네트워크 동작을 바꾸는 일은 총괄·사용자가 정할 일이다. 봇 하네스만 자기 서버 호스트의 제한을 푼다. 제안은 `docs/15` §16.6에 적었다.

### 2.7 2026-11-19 main(`2f5dd27`) 위로 다시 올리면서 정한 것

- 총괄 지시로 `git rebase main`을 한 번 했다. 충돌은 없었다(같은 파일을 고쳤어도 줄이 겹치지 않았다). `docs/12`는 §8 뒤 §9, `docs/15`는 §16.5 뒤 §16.6으로 번호 순서가 맞다.
- main이 더한 테스트 세 개는 모두 P1로 넣었다: `art_loop_test.gd`, `art_metrics_test.gd`(그림 루프 도구의 규칙과 지표 계산. 깨져도 게임은 돈다), `perf_bench_digest_test.gd`(성능 벤치 장면이 같은 시드에 같은 상태를 내는지. 벤치 도구의 계약이지 게임이 뜨는 조건이 아니다). 이제 P0 30개, P1 100개다.
- 변경 지도에 더한 줄: `art/`와 `tools/art_*` → 그림 루프 테스트, `tools/perf_bench*`와 `tools/perf_client.gd` → `perf_bench_digest_test`, `.claude/`(에이전트 스킬 문서) → 없음. `AGENTS.md`는 기존 `*.md` 줄로 문서 취급이다.
- 좀비·내비게이션 코드가 바뀔 때 `perf_bench_digest_test`도 돌릴지는 정하지 않았다(지시 범위 밖). 지금은 전체 검사에서만 같이 돈다.

### 2.6 그 밖에

- 봇은 실제 시간보다 4배 빠르게 돈다(`Engine.physics_ticks_per_second`와 `Engine.time_scale`을 같이 4배로 올려 틱 하나의 길이는 1/60초 그대로). 결과는 틱으로 세므로 배속과 무관하고, 느린 머신에서는 덜 빨라질 뿐이다.
- 지시서에는 `docs/12`의 새 절 번호가 `## 8`로 적혀 있었으나 기준 커밋(`84e271f`)에 이미 `## 8. 실제 프로세스 강제 종료·복구 점검`이 있어 `## 9`로 넣었다.
- 자동 검사 통과는 재미나 그림의 승인이 아니다. 봇이 장면을 깼다는 것은 "단순한 플레이어도 이길 수 있다"는 뜻일 뿐이다. 오히려 기준 결과에서 봇은 열린 땅에서 한 대도 맞지 않는다(docs/15 §16.6): 지금 좀비가 너무 쉬운지는 사람이 해 보고 정할 일이다.
